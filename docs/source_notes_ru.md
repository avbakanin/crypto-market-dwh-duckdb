# Источник: Binance Spot API — klines

- Endpoint: `GET https://api.binance.com/api/v3/klines`
- Зеркало для рыночных данных: `https://data-api.binance.vision`
- Параметры: `symbol`, `interval`, `startTime`, `endTime`, `limit` (по умолчанию 500, максимум 1000)
- Документация: https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints

## Поля (массив из 12 элементов)

| # | Поле | Тип в ответе | Пример (BTCUSDT, 2026-11-19 15:00 UTC) |
|---|------|--------------|------------------------------------------|
| 0 | open_time (мс, UTC) | int | 1795100400000 |
| 1 | open | string | "63558.00000000" |
| 2 | high | string | "63916.01000000" |
| 3 | low | string | "62780.07000000" |
| 4 | close | string | "63103.30000000" |
| 5 | volume (BTC) | string | "1213.38723000" |
| 6 | close_time (мс, UTC) | int | 1795103999999 |
| 7 | quote_volume (USDT) | string | "76724531.04007310" |
| 8 | trades_count | int | 206590 |
| 9 | taker_buy_base_volume | string | "631.83302000" |
| 10 | taker_buy_quote_volume | string | "39946372.67800280" |
| 11 | ignore | string | "0" |

## Наблюдения для Data Quality

1. **Ключ свечи — open_time.** Интервал `[open_time, open_time + 1h − 1ms]`; следующая свеча начинается с `close_time + 1 мс`.
2. **Последняя свеча может быть не закрыта.** 2026-11-19 в 17:22 UTC свеча 17:00 имела volume 509 BTC против ~1200 у закрытых. Правило: загружать только свечи с `close_time < now`.
3. **Цены и объёмы приходят строками**, чтобы не терять точность (quote_volume — до 16 значащих цифр). Хранить как `NUMBER(38, 8)`, не конвертировать во float.
4. **Время в Unix epoch, миллисекунды, UTC.** При конвертации в Python всегда указывать `tz=timezone.utc`.
5. **Объём выборки:** год часовых свечей ≈ 8760 строк, это минимум 9 запросов по 1000 на одну монету.
6. **Опечатка в тикере может молча вернуть другой инструмент.** `BTCUSD` (вместо `BTCUSDT`) отдаёт валидные данные с похожей ценой (+0.2%), но объёмом в ~16 000 раз меньше. Защита: фиксированный список тикеров (`dim_symbol` + dbt-тест `relationships`) и минимальный порог ликвидности.

## Наблюдения при отборе монет (whitelist)

Скрипт: `ingestion/select_symbols.py` → `config/symbols.csv` (будущий источник для `dim_symbol`).

7. **Неполная история у новых листингов.** У монеты, залистенной 3 месяца назад, ~2 200 часовых свечей вместо ~8 760 за год; при сравнении монет это выглядит как разрывы. → Правило: `first_candle_date` не позже чем 365 дней назад.
8. **Тикер ≠ актив.** Переименования разрывают историю между символами: LUNA → LUNC после краха Terra (май 2022), поэтому `LUNCUSDT` начинается с 2022-09-09. `first_candle_date` — дата листинга тикера, а не актива. → Не склеивать символы по имени base asset без таблицы соответствий.
9. **Не-крипто инструменты на споте.** Стейблкоины (новые появляются постоянно, например RWUSD в октябре 2026), токены на золото (PAXG, XAUT), токенизированные акции/ETF (NVDAB, QQQB, MSTRB, …). → Явный список исключений + правило по данным: диапазон close за 30 дней внутри [0.98, 1.02] ⇒ пег к USD, исключаем. Открытый вопрос: токенизированные акции сейчас отсекаются только правилом истории.
10. **Оборот за 24h — шумная метрика ликвидности.** MMTUSDT: 52.6M за 24h против 2.3M в среднем за 30 дней (×22); LUNCUSDT ×9; SKYUSDT ×8. Снимок за один день дал 3 ложных срабатывания из 24. → Правило: средний дневной оборот за 30 дней ≥ 10M USDT.
11. **Whitelist — это снимок.** Обороты меняются ежедневно, перезапуск скрипта меняет список. → `config/symbols.csv` коммитится в git и пересобирается только осознанно; `selected_at_utc` фиксирует момент.

## Наблюдения о поведении API

12. **Семантика ошибок.** Ошибки приходят с JSON-телом `{"code": ..., "msg": ...}`, например `HTTP 400 {"code":-1121,"msg":"Invalid symbol."}`. 4xx — наша ошибка, не ретраим. 429 — rate limit, может содержать `Retry-After` (секунды). 418 — бан IP после игнорирования 429, не ретраим (повторы продлевают бан). 5xx — временная ошибка, ретраим с экспоненциальным backoff. → Реализовано в `ingestion/clients/binance.py`.
13. **Ожидаемое число строк — 8 759, а не 8 760.** `startTime` не выровнен по часу, Binance отдаёт свечи с `open_time >= startTime`, поэтому первая свеча — следующий полный час; текущий час отбрасывается как незакрытый. Проверено на всех 23 монетах: 8 759 строк, 0 дублей, 0 разрывов (as of 2026-11-19 18:31 UTC). Прямое подтверждение 2026-11-20: для as-of 19:40:05 UTC (`startTime` = 2025-11-20 19:40:05) первая свеча в RAW открывается в 20:00:00, а не в 19:00 (свеча, содержащая `startTime`). → Проверка количества строк должна ожидать 8 759 для окна в 365 дней от единого as-of момента.
14. **Без `startTime` klines отдаёт последние `limit` свечей, и последняя из них ещё не закрыта.** Проверено 2026-11-19 20:11 UTC: `BTCUSDT 1d limit=3` вернул два закрытых дня и сегодняшнюю свечу с `close_time > now`. С `startTime=0, limit=1` API отдаёт самую первую свечу (BTCUSDT: 2017-08-17), то есть дату листинга. → `select_symbols.get_daily_stats` запрашивает `limit = days + 1` и отбрасывает последнюю свечу (`[:-1]`). Здесь `[:-1]` правилен, в отличие от пагинации по `startTime` (п. 2), где на полных страницах все свечи закрыты. Оговорка: если торги остановлены, последняя свеча может быть уже закрыта, и `[:-1]` выбросит один нормальный день.
26. **Локальные часы — не часы Binance.** Пять вызовов `GET /api/v3/time` 2026-11-20: сервер впереди локальных часов на 1.34 с (round trip ~250 мс). `drop_unclosed` и `batch_id` берут локальное время: если локальные часы *спешат*, свеча считается закрытой раньше настоящего закрытия на величину расхождения, пока её объём ещё меняется. Здесь расхождение в безопасную сторону. → Инкрементальный extract перечитывает последнюю выгруженную свечу (`OVERLAP_CANDLES = 1`): взятая слишком рано свеча придёт в финальном виде следующим запуском, а staging возьмёт версию из самого свежего батча. Время сервера как as-of не используем (лишний запрос); вернуться, если расхождение окажется в опасную сторону.
27. **Закрытые свечи не меняются.** Последние 48 закрытых часовых свечей батча `20261120T194005Z` (выгружен через 40 минут после закрытия последней) сравнили с живым API примерно через час: 1 104 свечи, 0 расхождений. После первой инкрементальной загрузки 23 свечи стыка, попавшие в оба батча, в RAW совпали байт в байт (`COUNT(DISTINCT TO_JSON(payload)) = 1` на свечу). → HWM-инкремента достаточно, CDC не нужен; перекрытие в 1 свечу — дешёвая страховка, а тот же запрос к RAW — детектор правок, который стоит гонять и дальше.
28. **Границы `startTime` и цена запросов.** `startTime`, равный `open_time` свечи, возвращает эту свечу первой (включительно); `startTime` в будущем → `[]`; `startTime` на текущем часе → только незакрытая свеча. Вес `GET /api/v3/klines` — 2 при любом `limit`; `exchangeInfo` сообщает лимит `REQUEST_WEIGHT` 6 000 в минуту, заголовок `X-MBX-USED-WEIGHT-1M` — израсходованный вес (2026-11-20). → Инкремент начинается ровно с HWM, чтобы перечитать эту свечу; символ, у которого HWM уже равен последней закрытой свече, пропускается без запроса — запуск без нового стоит 0 веса вместо 46 (23 × 2).
51. **Рост на +20 % за час у ликвидных монет почти не бывает.** За год по 23 монетам whitelist (201 894 часовые доходности close-to-close; landing zone и Snowsight совпали до строки, 2026-11-21): p99 = +2.70 %, p99.9 = +5.35 %, p99.99 = +9.26 %, максимум +20.44 % (INJUSDT, 2026-02-19 01:00) — единственный час с ростом от 20 %. От 15 % — 4 часа; от 10 % — 14; от 5 % — 254 часа у 21 символа (максимум BTCUSDT — +4.08 %). Соседние часы одного движения (WLDUSDT 2026-01-28 21:00 +19.4 % и 22:00 +15.2 %) с cooldown 24 ч схлопываются в 189 эпизодов. 2026-11-15 02:00 девять символов выросли на 5 % и больше в один и тот же час: это движение рынка, а не памп одной монеты. История open interest (с 2026-10-22, п. 36) даёт полное окно ±24 ч только 14 из 189 эпизодов. → Порог пампа — 5 % (dbt var); ширина рынка и z-score доходности остаются в витрине, а выводы об open interest указывают размер выборки. Пампы на +20 % — свойство неликвидных монет, которые отсекает whitelist.
52. **У часового объёма тяжёлый правый хвост.** z-score `quote_volume` относительно предыдущих 168 часов превышает 5 в 1 774 часах года, у всех 23 символов; z-score `ln(quote_volume)` — в 24 часах, у 14 символов. Часов с нулевым объёмом нет. → Warn на аномальный объём считается по логарифму; мутация R6 (сырой объём) превращает его 24 строки в 1 774.

## Наблюдения о фьючерсном API Binance (USD-M)

Эндпоинты `https://fapi.binance.com` для funding rate и open interest; живые пробы 2026-11-20/21 по 23 монетам whitelist.

30. **Доступ и лимиты.** `fapi.binance.com` отвечает из Черногории без VPN; локальные часы отставали от фьючерсного сервера на 1.77 с (безопасное направление, как в п. 26). `exchangeInfo` сообщает лимит `REQUEST_WEIGHT` 2 400 в минуту (спот — 6 000). История funding делит отдельный лимит 500 запросов за 5 минут с `fundingInfo`; история open interest — 1 000 запросов за 5 минут. Эти два эндпоинта не возвращают заголовок `X-MBX-USED-WEIGHT`, расход по ответу не узнать. → Первый прогон — около 50 запросов funding и 46 open interest, ежечасный — около 23 запросов open interest и ни одного funding между расчётами; extract делает паузу 0.2 с между страницами.
31. **Спот-символ ≠ символ фьючерса; подстрока врёт.** У 22 из 23 монет USD-M perpetual с тем же символом; `PEPEUSDT` соответствует `1000PEPEUSDT` (`baseAsset` `1000PEPE`, цена за 1 000 монет). Поиск по подстроке символа находит чужие контракты: `BTCDOMUSDT` (индекс доминации BTC), `PUMPBTCUSDT` (другая монета, статус `SETTLING`), `ETHFIUSDT`, `ETHWUSDT`. Квартальные контракты имеют тот же `baseAsset` (`BTCUSDT_261225`), а `contractType` `TRADIFI_PERPETUAL` помечает токенизированные акции (`OPENAIUSDT`, `UNITREEUSDT`) — явный признак, которого нет в спотовом `exchangeInfo` (п. 9). → `map_perpetuals` сравнивает `baseAsset` (с префиксом `1000`, `1000000` или `1M` или без), `contractType = PERPETUAL`, `status = TRADING`, котировку USDT и хранит множитель в `config/perpetuals.csv`; два кандидата на одну монету останавливают сопоставление.
32. **История funding: включительный `startTime`, первые `limit`, а `startTime=0` значит «не передан».** `startTime`, равный `fundingTime` записи, возвращает её первой, с точностью до миллисекунды; при диапазоне шире `limit` (максимум 1 000) приходят первые `limit` записей по возрастанию; `startTime` в будущем → `[]`. `startTime=0` считается отсутствующим и возвращает самые свежие записи, а не самые ранние (у спотовых klines — дату листинга, п. 14). История BTCUSDT начинается 2019-09-10; у старых записей `markPrice` — `""` (пустая строка), у записей последнего года значение есть; `rateType` — `Regular` (документация оставляет `Special` для дивидендов по акциям). → Пагинация вперёд от последнего `fundingTime + 1`; клиент отвергает `start_time <= 0`; staging должен считать пустой `markPrice` NULL, а не кастовать его.
33. **`fundingTime` приходит через несколько миллисекунд после часа.** За год расчётов BTCUSDT 461 из 1 000 ровно на часе, остальные на 1–26 мс позже (`00:00:00.007`). → Ключ сетки — час (`fundingTime // 1 ч`): проверки дублей и разрывов в extract, подсчёт дублей в RAW загрузчиком (`FLOOR(fundingTime / 3600000)`) и staging используют один ключ.
34. **Интервал funding разный у контрактов и меняется со временем.** 19 из 23 контрактов рассчитываются каждые 8 ч, ENA, PUMP, TAO и ASTER — каждые 4 ч (сетка от 00:00 UTC). `fundingInfo` перечисляет только контракты с изменённым cap, floor или интервалом (833 из 956); у `GTCUSDT` там сейчас 4 ч, а в июне 2026 расчёт шёл каждые 8 ч. Истории интервалов API не отдаёт. → Extract берёт текущий интервал (8 ч, если контракта нет в списке) и записывает его по файлу (`interval_hours`); `expected` — оценка, поэтому расхождение — DQ-предупреждение, а не стоп.
35. **Платформа пропускает расчёты.** Расчёта 2026-06-24 04:00 нет у 20 из 21 проверенного контракта, которые в тот день рассчитывались каждые 4 ч (ENA, PUMP, TAO, ASTER, LPTUSDT, KERNELUSDT и другие); есть только у IRYSUSDT. У 8-часовых контрактов в этот час расчёта нет по сетке. Поэтому первая годовая выгрузка показывает у четырёх 4-часовых контрактов `rows=2189, expected=2190, gaps=1`. → Реальная дыра источника, пойманная DQ-проверкой: сообщить, пометить в staging, не интерполировать.
36. **История open interest — около месяца, а более старое время — ошибка.** `openInterestHist` отдаёт скользящие 744 часовые точки (~31 день); `startTime` или `endTime` старше — `HTTP 400 {"code":-1130,"msg":"parameter 'startTime' is invalid."}`, а не пустой ответ (4xx не повторяется). В документации максимум `limit` — 500, но 501 и 1 000 принимаются (1 000 вернул все 744 точки). Метки ровно на часе; по документации период без сделок точки не имеет. → RAW — единственная копия open interest старше месяца, поэтому extract нужно запускать минимум раз в 30 дней; он запрашивает не больше 30 дней (день запаса от скользящей границы), точки, выпавшие из окна, отчитывает как `lost`, `limit` держит на документированных 500.
37. **Open interest листается в обратную сторону: ПОСЛЕДНИЕ `limit` точек.** При одном `startTime` или при `startTime` и `endTime`, охватывающих больше `limit` точек, приходят самые новые `limit` точек диапазона; klines и funding отдают самые старые. Пагинация вперёд по `startTime`, как у свечей, вернула бы новейшие 500 из 720 точек и молча потеряла первые 220. → Страницы — явные окна не шире 500 часов (`startTime` и `endTime = startTime + 499 ч`): окно не шире `limit` приходит целиком. Два окна дают 720 точек за 30 дней без дублей.
38. **Точка open interest T публикуется примерно через минуту после T и не меняется.** При опросе около 22:00 UTC 2026-11-20 точка 22:00 появилась через 61–76 с после начала часа; она и три предыдущие точки сохранили значения в следующие 7 и 20 минут. Документация описывает `timestamp` как конец периода. → Точка ожидается через 5 минут после своего времени (`PUBLISH_LAG_MS`), иначе запуск в начале часа выдал бы ложное «нет новых точек»; отметки уровня достаточно, перекрытие в одну точку доказывает стык. Задержка публикации funding ещё не измерена; принят тот же лаг 5 минут.
39. **Funding большую часть времени равен процентной ставке: повторяющееся значение — формула, а не зависшие данные.** FAQ Binance (обновлён 2026-03-06): `F = [P + clamp(I − P, 0.05%, −0.05%)] / (8 / N)`, процентная ставка `I` = 0.01 % за 8 ч для большинства символов; пока индекс премии между −0.04 % и 0.06 %, `F` равен `I`. В RAW (2025-11-21 — 2026-11-21) максимум ставки ровно `0.00010000` у 12 из 19 восьмичасовых контрактов и `0.00005000` (0.01 % / (8 / 4)) у 2 из 4 четырёхчасовых; минимумы уходят далеко вниз (INJUSDT −0.01183133, TAOUSDT −0.00359598). Все ставки — JSON-строки (`VARCHAR` в `VARIANT`) и точно приводятся к `NUMBER(38, 8)`. → DQ-проверка «значение не менялось N периодов» сработала бы на здоровых данных funding; сравнивать funding с `I / (8 / interval_hours)`, а не с прошлым значением, и помнить, что у 4-часовых контрактов ставка за 4 ч.
41. **Процентная ставка — у каждого контракта своя: у BNBUSDT её нет.** Живой `GET /fapi/v1/premiumIndex` (2026-11-21, без символа: все контракты одним запросом) даёт `interestRate = 0.00000000` у BNBUSDT и `0.00010000` у остальных 22 контрактов, включая 4-часовые: ставка номинирована за 8 ч, и 4-часовой расчёт платит `0.0001 / (8 / 4) = 0.00005`. Модальный funding BNBUSDT за год в RAW ровно 0 (55 % расчётов): при `I = 0` и спокойной премии формула из п. 39 ничего не платит. Спот против фьючерса за тот же год: `close` свечи, закрывающейся в момент расчёта, и mark price за монету (`markPrice` / множитель) расходились не больше чем на 0.87 % (TRXUSDT); пустого `markPrice` в окне нет ни у одной записи. → `config/perpetuals.csv` хранит `interest_rate_8h` по контракту (снимок: истории API не отдаёт), а проверка в staging сравнивает модальный funding каждого контракта с его собственным `interest_rate_8h * interval_hours / 8`. Проверка с константой 0.01 % из FAQ помечает BNBUSDT на здоровых данных (мутация Q7: ровно эта одна строка).
81. **Эндпоинты long/short ratio хранят 30 дней, как open interest.** Живая проба (2026-11-22, BTCUSDT, `period=1h`): `topLongShortAccountRatio`, `topLongShortPositionRatio`, `globalLongShortAccountRatio` и `takerlongshortRatio` (все под `/futures/data/`) отдают окно, начинающееся 29 или 30 дней назад, а на 31 и 32 дня отвечают HTTP 400 `-1130` «parameter 'startTime' is invalid» — тот же скользящий предел, что у `openInterestHist` (п. 36). `takerlongshortRatio` не возвращает `symbol` (только `buySellRatio`, `buyVol`, `sellVol`, `timestamp`), и его последняя точка в тот же момент была на час старше, чем у трёх других. → Четвёртый датасет — по шаблону OI (окна с `endTime`, символ из имени файла) со своим лагом публикации, который надо измерить; каждый день отсрочки теряет один день в начале истории, а не всю историю.
89. **Три эндпоинта long/short — снимки, taker — объём часа с меткой его начала.** Живая проба (2026-11-22): точки `topLongShortAccountRatio`, `topLongShortPositionRatio` и `globalLongShortAccountRatio` стоят на ровном часе, самая свежая — только что закончившийся час, как у open interest: снимок на `timestamp`. `takerlongshortRatio` с `timestamp = T` совпадает с taker-объёмом покупок и продаж фьючерсной часовой свечи, открытой в T (`/fapi/v1/klines`, поле 9 и поле 5 минус 9), и чуть меньше (до 0.02 %: 4343.273 против 4343.895 BTC), а окно фильтруется по концу периода (`startTime` 18:22 вернул точку с меткой 18:00). «Последняя точка на час старше» из п. 81 — это и есть причина, а не задержка публикации. → Выгружаются три ratio (каждый в свою RAW-таблицу: payload одной формы, ряд различает только таблица); taker пропущен — фьючерсные свечи хранят тот же объём годами, а не 30 дней.
90. **Пагинация и лимиты — как у open interest.** Все четыре эндпоинта отдают ПОСЛЕДНИЕ `limit` точек диапазона `[startTime, endTime]` (обе границы включительно), отвечают HTTP 400 `-1130` на `startTime` 31-дневной давности и не присылают заголовков `X-MBX-USED-WEIGHT` (по документации: вес 0, свой лимит 1000 запросов за 5 минут). `limit=1000` принят, хотя документирован максимум 500 (вернулись все 720 точек окна). У всех 23 контрактов по 720 часовых точек в каждом эндпоинте, без разрывов. → Один алгоритм extract для всех рядов /futures/data/ (`futures_stats.py`, окна по 500 ч с `endTime`); open interest стал одной из его конфигураций.
91. **Доли приходят округлёнными, ratio — нет: фиксированный допуск ломается на больших ratio.** `longAccount` и `shortAccount` — 4 знака, в сумме всегда 1; `longShortRatio` — long / short неокруглённых долей. Проверка `|ratio − long/short| <= 0.0006` отметила 963 из 16 560 строк `topLongShortPositionRatio` (ratio до 5.5, доля short до 0.15: ошибка округлённой доли растёт как 1/short); границы, которые допускает округление, `(long ∓ 0.00005) / (short ± 0.00005) ∓ 0.00005`, не отмечают ни одной из 48 024 строк трёх рядов. Медианы по 23 контрактам за 30 дней: все счета 1.70, топ-счета 2.11, топ-позиции 1.92. → Стоп-тесты в staging: доли в [0, 1] с суммой 1 ± 0.0001 и ratio в границах округления. Перепутанные колонки долей проходят первый и останавливаются только вторым (мутант E2: 49 674 из 49 680 строк; остальные 6 — часы ровно 0.5 / 0.5).
92. **Каждая точка /futures/data/ появилась за три минуты и не менялась.** Опрос раз в 5 с около 2026-11-22 19:00 UTC (BTCUSDT): `topLongShortAccountRatio` отдал точку 19:00 через 33 с, `takerlongshortRatio` свою точку 18:00 — через 84 с, `globalLongShortAccountRatio` — через 132 с, `openInterestHist` — через 137 с (2026-11-20 было 61–76 с), `topLongShortPositionRatio` — через 164 с; к 19:04 новая точка была у всех контрактов во всех эндпоинтах. Через минуту первые увиденные точки не изменились, 696 точек, бывших и в снимке 18:25, — тоже. → Лаг публикации 5 минут и расписание в :07 подходят и новым рядам; лаг одного эндпоинта меняется ото дня ко дню, поэтому туже его не настраиваем.

## Наблюдения о платформе: Snowflake

Trial-аккаунт создан 2026-11-20 (edition Standard, `AWS_US_EAST_2`). Скрипт настройки: `snowflake/setup.sql`.

15. **Выбранная роль — не единственная действующая.** У пользователей по умолчанию `DEFAULT_SECONDARY_ROLES = ('ALL')`, поэтому права дают все роли, выданные пользователю. Под `CRYPTO_DWH_ROLE`, у которой нет `OWNERSHIP` на схемы, `DROP SCHEMA CRYPTO_DWH.RAW` прошёл; в `ACCOUNT_USAGE.QUERY_HISTORY` у этого оператора `secondary_role_stats = {"roleCount":4,...}`. После `USE SECONDARY ROLES NONE` он падает с «Insufficient privileges ... must have OWNERSHIP». Snowsight сам выполняет `USE SECONDARY ROLES ALL` в своих сессиях; у вкладки одна сессия на все запуски, и `USE ROLE` secondary roles не сбрасывает. → Наименьшие привилегии обеспечиваются набором ролей у пользователя: загрузчику — отдельный service-пользователь только с проектной ролью. Негативные тесты прав запускать с выключенными secondary roles, иначе проверяется пользователь, а не роль.
16. **«Does not exist or not authorized» означает любое из двух.** `CREATE TABLE` в удалённой схеме и `USE WAREHOUSE` без `USAGE` дают ошибку одного вида: Snowflake не раскрывает роли, которая не видит объект, существует ли он. → При отладке сначала проверить существование объекта под админской ролью, потом подозревать гранты (и наоборот).
17. **Новый trial-аккаунт приходит с warehouse, которые простаивают по 5 минут.** Форма регистрации назначила облачный регион и edition, не спрашивая. Snowflake заранее создал `COMPUTE_WH` (default пользователя) и `SNOWFLAKE_LEARNING_WH` с `AUTO_SUSPEND = 300`, плюс `SYSTEM$STREAMLIT_NOTEBOOK_WH` с 60; все X-Small, Gen2 (`STANDARD_GEN_2`), владелец `ACCOUNTADMIN`. Gen2 — default для новых warehouse и на AWS стоит ×1.35 кредитов Gen1; `STATEMENT_TIMEOUT_IN_SECONDS` по умолчанию — 2 суток. → `setup.sql` создаёт проектный warehouse с явным `GENERATION = '1'`, `AUTO_SUSPEND = 60`, таймаутом 600 с и применяет те же лимиты простоя и таймаута к созданным заранее warehouse.
18. **Операции с метаданными не будят warehouse; `updated_on` — не журнал изменений.** `USE`, `SHOW`, `CREATE`/`DROP TABLE` и context-функции выполнялись при suspended `CRYPTO_WH` (`resumed_on` остался на последнем реальном запросе). `updated_on` менялся при холостом `ALTER ... SET` с теми же значениями и при каждом пробуждении. → Считать кредиты по метрингу warehouse, а не по числу запросов; дрейф конфигурации отслеживать сравнением свойств с `setup.sql`, а не по `updated_on`.
19. **Trial выдаёт роль PUBLIC, то есть всем пользователям.** При создании аккаунта `SNOWFLAKE_LEARNING_ROLE` выдаётся роли `PUBLIC`: `USAGE`/`OPERATE` на `SNOWFLAKE_LEARNING_WH` (Gen2, не под дневным монитором проектного warehouse) и `CREATE SCHEMA` в `SNOWFLAKE_LEARNING_DB`. Service-пользователь `CRYPTO_LOADER`, которому выдана только проектная роль, всё равно мог ей пользоваться: `SHOW GRANTS TO USER` показывал одну роль, а `CURRENT_AVAILABLE_ROLES()` в smoke-проверке вернул три. → Проверять эффективные роли, а не прямые гранты. `setup.sql` выдаёт роль админу и отзывает у `PUBLIC`; добавить её в ожидаемые роли значило бы узаконить утечку.
20. **Неверный пароль от ключа выглядит как отказ сервера.** Когда в `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` по ошибке оказался публичный ключ, коннектор 5.2.0 выдал `250001 (08001): Failed to login: Authentication failed. Unspecified`, но в `LOGIN_HISTORY_BY_USER` попытки нет (следующий, успешный вход записан с `RSA_KEYPAIR`). Судя по всему, сбой был на клиенте (ключ не расшифровался), а сообщение говорит обратное. → При «Authentication failed» сначала смотреть журнал входов: записи нет — проблема на клиенте (пароль, файл ключа); запись есть — в ней `error_message` сервера.
21. **COPY пропускает уже загруженный файл, только пока тот не изменился, и сообщает об этом по каждому файлу.** Load metadata хранится по таблице 64 дня (имя файла, размер, ETag, число строк). `FORCE` описан как загрузка файлов «regardless of whether they were loaded previously and haven't changed», то есть изменённый файл с тем же именем загрузится снова. Повторный `COPY ... FILES = ('BTCUSDT.json.gz')` для загруженного файла вернул одну строку: `status = LOAD_SKIPPED`, `errors_seen = 1`, `first_error = "File was loaded before."`, таблица не изменилась. Сообщения «Copy executed with 0 files processed.» не было (2026-11-20). → Extract пишет неизменяемые каталоги батчей (`<batch_id>/<SYMBOL>.json`), файл под загруженным именем никогда не меняется; загрузчик считает `LOAD_SKIPPED` остановкой, решение принимает человек (`TRUNCATE` очищает load metadata, `FORCE` её игнорирует).
22. **PUT отвечает `SKIPPED` на другой файл с уже существующим именем и оставляет старый.** При `OVERWRITE = FALSE`, коннектор 5.2.0: PUT нового файла → `UPLOADED`; тот же файл ещё раз → `SKIPPED`; файл с тем же именем и новым содержимым → тоже `SKIPPED`, `message` пустой, а `LIST` показывает прежние размер и MD5 (эксперимент в отдельном каталоге stage, 2026-11-20). По ответу PUT эти два случая не различить. → Каталог батча никогда не перезаписывается (extract падает, если каталог есть). Известное ограничение: если загруженный в stage батч поправить локально (вместе с манифестом) и перезапустить, COPY загрузит старую версию из stage; сверка поймает это, только если изменилось число строк. Сравнить MD5 локального и staged-файла нельзя: gzip у разных компрессоров даёт разные байты (время в заголовке, настройки).
23. **Метаданные файла в COPY: относительный путь, MD5, номер элемента.** `METADATA$FILENAME` — путь внутри stage (`20261120T194005Z/BTCUSDT.json.gz`), а `LIST` и результат COPY добавляют имя stage (`klines_stage/20261120T194005Z/...`). `METADATA$FILE_CONTENT_KEY` совпадает с MD5, который `LIST` показывает для файла в stage (сжатого). При `STRIP_OUTER_ARRAY = TRUE` `METADATA$FILE_ROW_NUMBER` — позиция элемента массива с 1, в порядке файла (1..8759, `LAG` по нему не находит нарушений порядка). → Разбирать путь с конца (`SPLIT_PART(..., -1)`), а не по фиксированному префиксу; `_file_content_key` указывает точную версию файла, из которой пришла строка.
24. **Вывод `TIMESTAMP_LTZ` следует поясу сессии, а он по умолчанию — тихоокеанское время США.** `COPY_HISTORY.LAST_LOAD_TIME` и `created_on` в выводе `SHOW` пришли с `-0800`, что соответствует поясу сессии по умолчанию `America/Los_Angeles`. → Хранимые метки времени конвертируются явно: `_loaded_at = CONVERT_TIMEZONE('UTC', METADATA$START_SCAN_TIME)` (2-аргументная форма возвращает `TIMESTAMP_TZ`), и RAW читается одинаково из любой сессии (п. 4).
25. **JSON-строки остаются строками в `VARIANT`.** Binance шлёт цены JSON-строками; в RAW `TYPEOF(payload[1])` = `VARCHAR`, а `payload[1]::NUMBER(38, 8)` даёт точное десятичное число (`"86921.27000000"` → `86921.27000000`), `open_time` — `INTEGER`. → Цены приводить к `NUMBER(38, 8)` в staging, никогда через `FLOAT`/`TO_DOUBLE` (п. 3).
29. **Какие запросы шли на warehouse, показывает `WAREHOUSE_SIZE` в `QUERY_HISTORY`, а не `WAREHOUSE_NAME`.** У `CRYPTO_LOADER` (`INFORMATION_SCHEMA.QUERY_HISTORY_BY_USER`, 2026-11-20) у всех операторов `WAREHOUSE_NAME = CRYPTO_WH` (текущий warehouse сессии), но `WAREHOUSE_SIZE` заполнен только у `SELECT DISTINCT _batch_id`, `SELECT` статистики батча и `COPY`. У DDL (`CREATE ... IF NOT EXISTS`, `ALTER ... SET`), `PUT` и `SELECT` из context-функций в smoke-проверке он пуст. Холостой запуск загрузчика выполнил один оператор на warehouse (`SELECT DISTINCT`, 180 мс); он пришёл через 18 с после предыдущего запуска и застал warehouse работающим. Первый `SELECT DISTINCT` предыдущего запуска занял 720 мс. → Подтверждает п. 18 для `PUT` и DDL. Холостой запуск загрузчика стоит одного resume (минимум 60 с X-Small), если не попадает в окно `AUTO_SUSPEND` после другой работы; сделать его бесплатным — только не запускать (оркестрация или метка в stage, читаемая через `LIST`).
40. **Кэш результатов запросов сделал холостые запуски загрузчика бесплатными.** Четыре запуска `load_raw` за минуту (2026-11-21 11:56 UTC) — четыре сессии с 11, 3, 0 и 0 операторами на warehouse (`WAREHOUSE_SIZE` заполнен). Полная модель для первого запуска — 12 (3 lookup + 3 × статистика батча, `COPY`, статистика): его lookup свечей `SELECT DISTINCT _batch_id FROM RAW.BINANCE_SPOT_KLINES_1H` совпал по тексту с запуском прошлого дня, а таблица с тех пор не менялась, и Snowflake ответил из кэша результатов без warehouse. Второй запуск повторил все три lookup после того, как `COPY` первого изменил таблицы, — все три пошли на warehouse; третий и четвёртый застали таблицы неизменными и на warehouse ничего не выполнили. Картина 11 / 3 / 0 / 0 в точности совпадает с правилами кэша (тот же текст, таблица с тех пор не менялась). → Холостой запуск ничего не стоит, если с прошлого такого же lookup ничего не грузили; resume оплачивается только сразу после загрузки. Уточняет п. 29, где холостой запуск через 18 с после загрузки использовал warehouse; общим ответом остаётся пропуск холостых запусков оркестрацией (неделя 4).
42. **Ошибки прав теперь называют недостающую привилегию и primary role.** С `USE SECONDARY ROLES NONE` (2026-11-21) Snowsight вернул, например, «Insufficient privileges to operate on schema 'RAW'. Your primary role CRYPTO_DWH_ROLE must have CREATE VIEW granted on SCHEMA CRYPTO_DWH.RAW», а для схемы без `USAGE` — «Schema 'CRYPTO_DWH.STAGING' does not exist or not authorized. Your primary role ... must have USAGE or any other privilege granted on SCHEMA ...». `USE WAREHOUSE COMPUTE_WH` без `USAGE` по-прежнему дал общее «Object does not exist, or operation cannot be performed.» → П. 16 остаётся в силе (существование объекта не подтверждается), но подсказка говорит, какого гранта не хватает и что проверялась только primary role — это заодно доказывает, что secondary roles были выключены.
43. **Грант, выданный через MANAGE GRANTS, записывается от имени владельца объекта.** `GRANT SELECT ON ALL TABLES IN SCHEMA CRYPTO_DWH.RAW TO ROLE CRYPTO_TRANSFORMER`, выполненный под `SECURITYADMIN`, в `SHOW GRANTS TO ROLE CRYPTO_TRANSFORMER` показан с `granted_by = CRYPTO_DWH_ROLE` — владельцем RAW-таблиц; гранты на схемы, выполненные под `SYSADMIN`, показывают `SYSADMIN`. `SHOW FUTURE GRANTS IN SCHEMA` показывает future grant как `CRYPTO_DWH.RAW.<TABLE>`. → `SHOW GRANTS` отвечает, какие права действуют, но не кто их выдал; аудит грантов — по `QUERY_HISTORY` (текст оператора, роль, пользователь).
44. **Именованные ключи живут отдельно от слотов `RSA_PUBLIC_KEY`.** После `ALTER USER ... ADD KEY PAIR` `DESC USER` показывает `HAS_KEYPAIR = true`, а `RSA_PUBLIC_KEY` и `RSA_PUBLIC_KEY_FP` остаются пустыми (CRYPTO_LOADER); сам ключ виден в `SHOW USER KEY PAIRS FOR USER <имя>`: имя (в верхнем регистре, `DBT_KEY_1`), отпечаток, статус и `last_used_on`. Регистрация ключа, которая не выполнилась (запустился только `DESC` под курсором), выглядела как `HAS_KEYPAIR = false` и пустой список. → Ключ проверяется сравнением отпечатка из `SHOW USER KEY PAIRS` с выводом генератора; `last_used_on` перед ротацией показывает, используется ли ключ.
45. **Прогон dbt стоит одно пробуждение warehouse; пересборка сбрасывает result cache.** Для `CRYPTO_DBT` 2026-11-21 (`QUERY_HISTORY_BY_USER`, `query_tag = crypto_dwh_dbt`): каждый запуск dbt после простоя больше 60 с будил `CRYPTO_WH` один раз; `dbt build` из 3 моделей, 43 data tests и 3 unit tests занял 13 с в 4 потока и 6 сессиях, а десять запусков dbt с паузами 10 с уложились в одно пробуждение. Час с пятью пробуждениями дал 0.1228 кредита compute — около 1.5 мин (0.025 кредита) на пробуждение, тогда как все `CREATE TABLE AS SELECT` моделей за этот час работали 25 с в сумме; cloud services — 5.7 % от compute (до 10 % не оплачиваются). `dbt test` на неизменившихся таблицах выполнил на warehouse 5 из 49 операторов: 44 `SELECT` тестов ответил result cache (0 байт прочитано), исключения — два теста сетки (`generator()`/`seq4()` в запросе) и `CREATE TABLE AS SELECT` фикстур unit-тестов. Сразу после `CREATE TABLE AS` в `dbt build` все тесты шли на warehouse. → Счёт определяется числом пробуждений, а не строк: dbt — одним запуском, и пропускать его, когда новых батчей нет (неделя 4). Полная пересборка неизменившихся данных платит за пересчёт и сбрасывает кэш; incremental-модели сохранили бы и то и другое (неделя 3, шаг 2).
53. **ASOF JOIN отвечает на вопрос «последний расчёт не позже часа».** `ASOF JOIN funding MATCH_CONDITION (hours.hour_end_ms >= funding.funding_hour_ms) ON hours.symbol = funding.spot_symbol` возвращает не больше одной правой строки на левую, а левую строку без совпадения дополняет NULL — как left join. По документации (прочитана 2026-11-21) условие совпадения принимает `>=`, `<=`, `>` или `<` на временных метках или числах, равные строки справа выбираются недетерминированно, а в примерах за ASOF JOIN идёт INNER или ещё один ASOF JOIN, но никогда не внешний join. На живых данных as-of колонки точно совпали с Python-эталоном: 421 час до начала истории funding, 16 часов stale в дыре 2026-06-24. sqlfluff 4.5 этот синтаксис разбирает. → Funding уникален по (контракт, час), а контракт и спот-символ соответствуют один к одному, поэтому равных строк нет; open interest присоединяется в CTE до ASOF JOIN. В Oracle то же делают через `LAST_VALUE(... IGNORE NULLS) OVER` поверх внешнего join.
54. **Marts не удорожили прогон dbt.** Полный `dbt build` 2026-11-21 (2 seeds, 8 табличных моделей, 89 data tests, 6 unit tests) занял 28 с в 4 потока и 8 сессиях; 97 из 140 его операторов выполнились на warehouse — 10.9 с выполнения в сумме, из них 8.9 с — восемь `CREATE TABLE AS SELECT`, прочитано 242 МБ. Это одно пробуждение, как и для одного staging (п. 45). Весь день сборки и мутационного тестирования дал на `CRYPTO_WH` 0.63 кредита compute (32 % дневного монитора) и 0.03 кредита cloud services: прогоны мутаций, замеры и проверки в Snowsight шли пачками с паузами дольше `AUTO_SUSPEND`, и каждая пачка оплачивала своё пробуждение. → Стоимость определяется числом отдельных пачек работы, а не размером проекта; интерактивные проверки собирать вместе, dbt — один раз на прогон пайплайна.
58. **Сохранение находок всех тестов утроило число операторов прогона, но не работу warehouse.** `QUERY_HISTORY_BY_USER` для `CRYPTO_DBT`, четыре полных build 2026-11-21: до шага 140 операторов, 97 на warehouse, 27.6 с; со `store_failures` для 90 тестов, хуками DQ-журнала и view `dq_check_results` — 353 оператора, 120 на warehouse, 51 с. Новые — 89 `CREATE VIEW` (стоп-тесты) и 100 `DROP` объектов прошлого прогона: ни один не идёт на warehouse, но каждый занимает 0.22 и 0.12 с; плюс ещё 11 `CREATE TABLE AS SELECT` (warn-тесты) и один `INSERT` (журнал). Выполнение на warehouse выросло с 10.7 до 18.0 с. В первом прогоне после включения `DROP` не было: схема DQ была пуста. В час прогонов (18:00 UTC) cloud services — 0.021 кредита против 0.207 compute, 10.4 %; за день — 6.4 %, ниже бесплатных 10 % от дневного compute (оплачивается только то, что сверх). → Прогон — по-прежнему одно пробуждение, теперь примерно на 23 с длиннее (≈ 0.006 кредита отдельной пачкой, ≈ 0.15 в сутки при ежечасном расписании). View не стоят warehouse, но переносят работу с метаданными в cloud services; при ежечасном расписании следить за его дневной долей, а если секунды станут важны — вернуть стоп-тесты в `ephemeral`, оставив warn-тестам таблицы.
59. **`INFORMATION_SCHEMA.TABLES` отвечает «сколько находок и когда записаны», не читая таблиц.** У таблиц находок `row_count` равен числу находок, которое записал dbt (4 и 24, 2026-11-21), а `created` сдвигается на время каждой пересборки (dbt удаляет и заново создаёт таблицу при каждом прогоне теста). В сравнении с `_logged_at` DQ-журнала (его ставит `current_timestamp()` в INSERT — тоже часы Snowflake) это показывает журнал, отставший от таблицы: мутант L4 (хук перестал писать тесты) сделал все 11 таблиц новее их последних строк журнала. → Сверка соединяет ожидаемые таблицы из графа dbt с `INFORMATION_SCHEMA.TABLES`: пропавшая таблица — находка, а не ошибка SQL, и время по часам машины с dbt никогда не сравнивается с серверным.
60. **Коннектор на Linux проверяет права файла приватного ключа.** В Linux-контейнере (Docker Desktop 4.99, 2026-11-21) `snowflake-connector-python` 5.2.0 отказался от `private_key_file`: «000006: Configuration error: Insecure file permissions on /run/secrets/snowflake_loader_key: File is writable by group or others». На Windows тот же файл и тот же код подключаются: проверять там нечего, POSIX-прав нет. Ключ, смонтированный с хоста Windows, внутри контейнера виден как `root:root 0777`, и `chmod` на него не действует (п. 64). dbt-snowflake это не затронуло: он сам расшифровывает ключ через `cryptography` и передаёт коннектору байты ключа, а не путь, поэтому `dbt debug` дошёл до (фиктивного) аккаунта. Параметры коннектора `unsafe_skip_*permissions_check` относятся к его конфиг-файлам и кэшу CRL, а не к ключу. → В контейнере `with-private-keys` перед каждой командой копирует ключ в файл только для владельца (0400 в каталоге 0700 на tmpfs); проверка остаётся включённой. Проверка безопасности, которая есть только в одной ОС, видна только в этой ОС: репетиция на одноразовом ключе поймала её до живого запуска.
75. **Прогон пайплайна стоит своего пробуждения, а cloud services становятся четвертью счёта.** Первые прогоны DAG (2026-11-22) занимали Snowflake по 87 с: загрузчик — 27 операторов (9 на warehouse, 1.5 с выполнения), dbt (freshness + build + сверка журнала) — 382 (125 на warehouse, 15.9 с). Метеринг насчитал 0.0808 кредита compute за два таких прогона, по 0.040: 87 с плюс хвост `AUTO_SUSPEND` 60 с, около 2.45 минуты X-Small Gen1. Cloud services в эти часы — 27 % от compute (0.0222), против 10.4 % в самый загруженный час Недели 4, Шага 1: прогон короткий, а операторов метаданных много (DROP и CREATE VIEW сохранённых находок, DESCRIBE, хуки). Cloud services оплачиваются сверх 10 % дневного compute, поэтому 8 прогонов в сутки стоят около 0.32 compute + 0.06 оплачиваемых cloud services = 0.38 кредита; ежечасно (около 1.1 в сутки) монитор аккаунта на 30 кредитов остановил бы warehouse на 90 % ещё до конца trial. `INFORMATION_SCHEMA.WAREHOUSE_METERING_HISTORY` с `DATE_RANGE_START` не на границе часа вернула часовые окна, выровненные по этому началу (07:18:58, 08:18:58), и одно окно сложило два прогона. → Вся цепочка — в одном пробуждении, расписание — раз в 3 часа; рычаг, если станет дорого, — вернуть стоп-тесты в `ephemeral` (п. 58); почасовой метеринг — от `DATE_TRUNC('hour', ...)`.
93. **Future grants сразу открыли новые RAW-таблицы.** Загрузчик создал три таблицы в RAW (2026-11-22, под `CRYPTO_DWH_ROLE`, своим DDL при старте), и сразу следующие `dbt source freshness` и `dbt build` прочитали их под `CRYPTO_TRANSFORMER` без правки `setup.sql`: `GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW` (Неделя 3) действует на каждую таблицу, созданную после него. → Новому датасету грант не нужен; новой схеме — нужен (future grants задаются на схему).
96. **Тип колонки в Arrow зависит от значений, а не от объявленного типа.** `fetch_arrow_all` коннектора 5.2.0 на витринах (проба 2026-11-24): целые пришли как int8, int16, int32 или int64 по самому большому значению результата (`episode_hours` int8, `events` int16, `failures` int32, `event_open_time_ms` int64), а при умолчании `arrow_number_to_decimal=False` дробные NUMBER(38, s) — как double, кроме `open_interest_coins_before` (NUMBER(38, 8)) — decimal128(38, 8), вероятно, потому что часть немасштабированных значений не влезает в int64 (1000PEPE в монетах). С `arrow_number_to_decimal=True` каждая дробная колонка — decimal128(precision, scale). TIMESTAMP_TZ приходит как `timestamp[ns, tz=UTC]` (DuckDB читает его как TIMESTAMPTZ_NS; `force_microsecond_precision` даёт обычные микросекунды); пустой результат — None, если не задан `force_return_table=True`. → Экспорт берёт тип каждой колонки из метаданных результата (int64, decimal128(p, s), UTC-время в микросекундах) и приводит с `safe=True`: схема файла не меняется от выгрузки к выгрузке, а одинаковые данные дали побайтно одинаковые Parquet-файлы на Windows и в Linux-контейнере.
97. **Future grants переживают CREATE OR REPLACE в dbt, гранты на сегодняшние объекты — нет.** `SELECT ON FUTURE TABLES/VIEWS IN SCHEMA MARTS/DQ` для `CRYPTO_REPORTER` выданы в 09:03 UTC (2026-11-24, раздел 8 `setup.sql`, плюс `ALL` на существующие объекты); прогон 09:07 пересоздал все витрины и все объекты находок, и экспорт в 09:10 прочитал все пять таблиц под `CRYPTO_REPORTER`. `SHOW GRANTS` записывает владельца (`CRYPTO_TRANSFORMER`) как `granted_by` у SELECT, выданных `SECURITYADMIN` (как в п. 43). С `SECONDARY ROLES NONE` RAW и STAGING — «does not exist or not authorized», CREATE TABLE, DELETE, INSERT и `ALTER WAREHOUSE ... RESUME` назвали недостающую привилегию. → Потребителю объектов dbt только на чтение нужны future grants на схему (или `grants` в dbt, заново на каждом build); гранты только на текущие объекты сломаются на следующем build.

## Наблюдения об инструментах: dbt

dbt Core 1.12.7 с dbt-snowflake 1.12.5 на Python 3.12, Windows, запуск из корня репо под service-user `CRYPTO_DBT`.

46. **dbt-snowflake 1.12.5 передаёт коннектору 5.2.0 параметры эпохи 4.x.** Каждая новая сессия печатает `UserWarning: Unknown parameter 'insecure_mode'` (а также `reuse_connections`, `ocsp_root_certs_dict_lock_timeout`) и `FutureWarning` коннектора про `enable_server_session_keep_alive_auto_detection`, который профиль dbt задать не может; с 4 потоками прогон печатает их до шести раз. Коннектор неизвестные параметры игнорирует: OCSP-проверка остаётся по умолчанию (включена), а переиспользование соединений — логика самого dbt, и она работает (`reuse_connections: True` в `dbt debug`). `pip check` чист: адаптер допускает `snowflake-connector-python>=4.2.0,<6.0.0`. → Безвредный шум, не глушим фильтром по шаблону (предупреждение со словом `insecure` должно оставаться видимым); перепроверить с dbt-snowflake 1.13. «Совместимо по диапазону версий» ≠ «протестировано с этой версией».
47. **dbt 1.12 сам загружает `.env`, ища его от рабочего каталога вверх.** `dbt/cli/main.py` вызывает `load_dotenv(find_dotenv(usecwd=True), override=False)` до разбора аргументов, поэтому `DBT_PROJECT_DIR=dbt` и `DBT_PROFILES_DIR=dbt` в корневом `.env` позволяют запускать любую команду dbt из корня репо; переменные оболочки важнее файла, а для ключа, записанного дважды, python-dotenv берёт последнее вхождение (в `.env` репо было две строки `SNOWFLAKE_ACCOUNT` с разными значениями, и загрузчик работал на второй). `private_key_path` открывается как есть: `~` не раскрывается, в отличие от `connection_params` загрузчика. Зашифрованный PKCS#8 (PBES2, AES-256-CBC) читается через `cryptography`, а неверный пароль падает локально с «Incorrect password, could not decrypt key» — в отличие от сообщения коннектора из п. 20. → `.env.example` перечисляет переменные dbt с абсолютным путём к ключу; секреты — с префиксом `DBT_ENV_SECRET_`, который dbt маскирует в логах.
48. **Что dbt умеет без аккаунта.** `dbt deps`, `dbt parse` и `dbt ls` работают офлайн с профилем, где значения `env_var()` фиктивные; `dbt compile` подключается, если не запустить его с `--no-introspect --no-populate-cache` — тогда модели и тесты рендерятся офлайн (проверено sqlfluff); unit-тесты офлайн не компилируются вовсе (фикстурам нужны типы колонок с warehouse). На Windows `dbt deps` пишет `package-lock.yml` с CRLF; `.gitattributes` коммитит его как LF. dbt читает seeds из каталога вне проекта (`seed-paths: ["../config"]`). → Модели и тесты репетируются офлайн (compile + sqlfluff + независимый Python-эталон ожидаемых чисел); unit-тесты и всё, что касается данных, — на аккаунте.
49. **Модели, вызывающей `is_incremental()`, нужно переопределение в каждом её unit test, и офлайн она не компилируется.** После добавления `is_incremental()` в `stg_binance__klines_1h` (2026-11-21) `dbt parse` упал для всего проекта: «Boolean override for 'is_incremental' must be provided for unit test 'klines_latest_batch_wins_not_latest_load'». Исправляет `overrides: macros: is_incremental: false`; unit test incremental-ветки задал бы `true`. После этого `dbt compile --no-introspect --no-populate-cache` упал уже в рантайме («connection never acquired for thread»): `is_incremental()` вызывает `adapter.get_relation`, а для этого нужен аккаунт. → Перевод модели в incremental затрагивает каждый её unit test; incremental-ветку репетируем офлайн, отрендерив её с условием, принудительно равным true.
50. **На таком объёме incremental merge оказался медленнее полной пересборки и дал ту же таблицу.** `stg_binance__klines_1h` 2026-11-21, 201 917 → 201 940 строк, один новый батч из 23 символов × 2 свечи (`QUERY_HISTORY_BY_USER`, `CRYPTO_DBT`). Полная пересборка: один `CREATE TABLE AS SELECT`, 1.2–1.5 с выполнения, 16.4 МБ прочитано, 2.2–3.0 с на узел dbt. Incremental `merge` (ключи из новых батчей, все их версии в RAW): временное представление, четыре `DESCRIBE`, `BEGIN`, `MERGE` (0.6 с выполнения, 28.6 МБ прочитано: вся целевая таблица и RAW), `COMMIT`, `DROP` — 4.4 с на узел dbt; холостой merge всё равно прочитал 14.3 МБ и занял 3.9 с. `hash_agg(*)` таблицы после merge совпал с хешем пересобранной. dbt напечатал для merge `SUCCESS 23` — только вставленные строки (23 обновлённые свечи перекрытия не показаны), и `ROWS_PRODUCED` у `MERGE` (201 941; у холостого — 24) — тоже не число изменённых строк. → Модели остаются таблицами с полной пересборкой: оба способа занимают секунды внутри одного пробуждения (п. 45), а merge всё равно читает целевую таблицу. Вернуться, когда пересборка займёт минуты: тогда merge с `incremental_predicates` или кластеризацией, чтобы отсечь целевую таблицу, и сравнение `hash_agg` с пересборкой как проверка корректности.
55. **`store_failures` заменяет, а не накапливает.** Материализация теста в dbt-core 1.12.7 удаляет прошлый объект, создаёт таблицу или view из запроса теста и затем считает находки `select count(*)` из сохранённого. Без конфига схемы объект попадает в `dbt_test__audit`, который проходит через `generate_schema_name` как любая custom schema; имя теста от 64 символов превращается в alias с хешем (`DBT_UTILS_EXPRESSION_IS_TRUE_S_1077…`). `limit` применяется и до сохранения, и до подсчёта, поэтому урезается и число находок. Unit-тесты находки не сохраняют. Сохранённый warn или fail печатает `See test failures: select * from CRYPTO_DWH.DQ.<alias>`. → Находки каждого прогона живут в DQ (warn-тесты — таблицами с читаемыми alias, стоп-тесты — view), их история — в журнале, который пишет хук; без `limit`.
56. **Что лежит в `results` в `on-run-end` — проверено на живом прогоне.** Один результат на выполненный узел, без хуков: `status` (`pass`/`warn`/`fail`/`error`/`skipped` у тестов, `success` у моделей), `failures` (NULL у моделей и пропущенных тестов), `execution_time`, `timing` (naive UTC), `message` и сам узел. Уровень теста — как в конфиге: `ERROR` (дефолт `TestConfig`) или `warn`, как записано в YAML. У generic-теста есть `attached_node` и `column_name`, у singular — ни того ни другого (только `depends_on.nodes`), unit-тест называет свою модель в `tested_node_unique_id`, seed зависит только от макросов. Статусы и уровни — подклассы `str`; коннектор 5.2 передаёт их как строки. `adapter.add_query(sql, bindings=...)` вызывается из Jinja (им пользуются seeds), а соединения Snowflake — с autocommit. В dbt 1.12 хуки проекта входят в итоги (`Finished running 2 project hooks`, `PASS=109` на 109 узлов плюс 2 хука), упавший хук — это ERROR и ненулевой exit code, а `dbt source freshness` тоже их запускает (`source_freshness_run_project_hooks` по умолчанию true). → Макрос журнала приводит каждое значение к обычной `str`, проверяет атрибуты, которых нет у типа узла, view приводит уровень к нижнему регистру, а при сверке итогов с журналом два хука вычитаются.
57. **Default-селектор действует только на команды без выбора.** С `default: true` в `selectors.yml` `dbt build` печатает `Using default selector pipeline` и пропускает тег `dq_log`. Явный `--select` отключает default-селектор, и косвенный выбор (eager) добавляет все тесты, которые читают выбранную модель: `dbt build --select dq_check_results` запустил бы сверку журнала внутри build, до того как хук запишет журнал. → Ручной выбор, который задевает DQ-view, дополняется `--exclude tag:dq_log`; `dbt ls --select ...` показывает, что попадёт в выборку.
61. **Установка dbt-core 1.12.7 скачивает бинарник с GitHub, а пакет приносит свои файлы.** `dbt-core` требует `dbt-core-experimental-parser>=2.0.11`, а у него на PyPI только sdist (2026-11-21): его build backend (`_dbt_sa_build`) скачивает wheel под платформу (`manylinux_2_28_x86_64`, `manylinux_2_28_aarch64`, `win_amd64`, два macOS) из релизов dbt на GitHub и сверяет sha256 из `assets.json`. Сборка с доступом только к PyPI падает, а `pip install --only-binary=:all:` пакет не находит; у остальных 65 закреплённых пакетов есть Linux-wheels под Python 3.12. `dbt deps` не нужны ни профиль, ни подключение. Установленный `dbt_utils` 1.4.1 содержит три файла с CRLF (`macros/sql/star.sql` и два CSV интеграционных тестов) и каталог с именем `integration_tests/.env`. В контейнере `docker compose run --rm` каталог `target/` не сохраняется, поэтому каждый запуск начинается с «Unable to do partial parsing because saved manifest not found» (около 3 с полного разбора). → Сборке образа нужен github.com, а не только PyPI; проверки на файлы `.env` и байты CR смотрят только на файлы проекта (`-type f`, без `dbt_packages`).
76. **Default-селектор молча выключил `dbt source freshness`.** Селектор `pipeline` (`fqn:*` минус `tag:dq_log`, п. 57) применяется и к `dbt source freshness` и не выбирает ни одного источника: `dbt ls --resource-type source` — пусто, с `--select source:binance` — три таблицы. Простой `dbt source freshness` напечатал «Nothing to do. Try checking your model configs and model specification args» и вышел с кодом 0, не запустив хуки проекта, — поэтому и в журнале DQ от него нет строки. 3 × PASS Недели 3 были до селектора; с Недели 4, Шага 1 проверка не делала ничего. Нашлось при чтении лога зелёной задачи Airflow в первом живом прогоне DAG; тесты DAG проверяли граф, а не то, что команда что-то выбирает. → DAG запускает `dbt source freshness --select source:binance`, тест DAG закрепляет команду, описание селектора об этом говорит. Зелёная задача — не выполненная проверка: читать, что именно проверено.
82. **Собственных артефактов dbt хватает для алерта, а упавший тест прячет тесты ниже себя.** `dbt build` и `dbt test` пишут `target/run_results.json`; `dbt source freshness` — только `target/sources.json` (его задача переопределяет `result_path`, dbt-core 1.12.7). У каждого результата теста есть `status` (`pass`/`warn`/`fail`/`error`), `failures`, `message` и `relation_name` — объект со строками находок при `store_failures`; хуки — результаты `operation.*`; у freshness — `max_loaded_at` и его возраст. В контейнере scheduler файлы переживают вызов, поэтому callback сразу после задачи читает их без подключения. 70. **`docker compose exec` не видит того, что экспортировал entrypoint.** `exec` запускает новый процесс с окружением из конфигурации контейнера, мимо entrypoint: в scheduler он показывает `SNOWFLAKE_PRIVATE_KEY_PATH=/run/secrets/...` (монтирование 0777), а у самого процесса scheduler (`/proc/7/environ`) — копии только для владельца от `with-private-keys`. Процессы LocalExecutor их наследуют, но их `/proc/<pid>/environ` перезаписан `setproctitle` и не читается; в образе нет `ps` и `pgrep`. Задача смоук-DAG показала оба ключа `ok` (только владелец), а та же проверка в контейнере scheduler мимо обёртки упала с «owned by uid 0». → То, что видит задача, проверяет задача (`check_environment` в `smoke_environment`), а не `exec`.

84. **Где Airflow 3.4 исполняет callback.** По исходникам образа: `on_success/failure/retry/skipped_callback` задачи — в процессе самой задачи, в `task_runner.finalize()`; при LocalExecutor это контейнер scheduler с его окружением и файлами. Callback-и DAG (`DagCallbackRequest`, причины `task_failure`, `timed_out`, `all_tasks_deadlocked`) и failure callback задачи, завершённой снаружи (heartbeat timeout, застряла в очереди, процесс убит: `TaskCallbackRequest`), — в dag-processor. Docstring `BaseNotifier` говорит, что callback-и «run on the Dag Processor», — это половина правды. Callback с исключением только логируется («Failed to run task callback») и ничего не меняет. Callback-и DAG пишут не в лог задачи и не в вывод контейнера, а в `/opt/airflow/logs/dag_processor/<дата>/dags-folder/<файл>.log` («Executing on_success dag callback»). → Секреты алерта — scheduler и dag-processor; callback должен иметь смысл без файлов scheduler; за тишиной следит сторож снаружи (п. 88).
85. **Таймаут прогона даёт два failure callback-а, падение задачи — один.** Репетиция с `dagrun_timeout` 40 с и задачей, спящей 300 с (2026-11-22): scheduler пометил прогон failed, незавершённую задачу — skipped и послал ей SIGTERM; задача завершилась с кодом −15 и вызвала свой `on_failure_callback`, а через секунду dag-processor вызвал callback DAG с причиной `timed_out`. Обычное падение задачи даёт одно сообщение: callback DAG на `task_failure` намеренно молчит, `on_failure_callback` вызывается только на последней попытке (`load_raw` прислал алерт на try 2/2, повтор молчал), а задачи `upstream_failed` callback-ов не вызывают. → Два сообщения на таймаут — ожидаемо, а не ошибка.
86. **Провайдера Telegram в образе нет, а его клиент пишет токен в лог.** В образе Airflow 3.4.0 есть провайдеры Slack, SMTP и HTTP, но нет `apache-airflow-providers-telegram` (в constraints 3.4.0: 4.10.1 с `python-telegram-bot` 22.8). Эта библиотека ходит через httpx, который на INFO пишет URL каждого запроса, а URL Bot API содержит токен (`/bot<token>/sendMessage`); `HttpHook` пишет URL только на DEBUG. → Алерт отправляют несколько строк на `urllib`: без пакетов в окружении Airflow, токен только в запросе, ошибки без URL; простой текст — подчёркивания в именах dbt-тестов ломают Markdown.
87. **`.airflowignore` заставляет Airflow 3.4 печатать собственное предупреждение об устаревании.** С `.airflowignore` в папке DAG (синтаксис glob, по умолчанию) разбор пишет `DeprecationWarning: GitWildMatchPattern ('gitwildmatch') is deprecated` из `file_discovery.py` Airflow и из `pathspec`: Airflow вызывает API, который устарел в его же `pathspec`. Игнорирование работает (`dags/alerting` импортируется из `sys.path`, а не разбирается как файлы DAG). → Безвредно и не нам чинить; перепроверить со следующим релизом Airflow.
88. **Тишину замечает только сторож снаружи.** Ничто внутри стека не сообщит, что стек не работает: выключенная машина, не стартовавший Docker Desktop, зависший scheduler или DAG на паузе алертов не шлют, а потерянный алерт только логируется (п. 84). healthchecks.io (2026-11-22: бесплатный план — 20 проверок и 100 записей журнала на проверку, расписания cron с поясом и grace time, интеграция с Telegram, лицензия BSD, можно поднять у себя) ждёт пинга; DAG пингует из своего success callback, включая прогоны, где все extract-ы пропущены. Проверка — `7 */3 * * *` UTC с grace 1 ч: пропавший пинг даёт алерт примерно через час после слота, поэтому упавший прогон алертит дважды (сообщение задачи сразу, сторож через час). → URL пинга — своего рода секрет (с ним любой сообщит «жив»); Snowflake ALERT на свежесть DQ-журнала будил бы warehouse на каждую проверку.
94. **Зелёный прогон DAG может выполнить вчерашний dbt-проект.** Смонтирован только `./dags`; `ingestion/` и `dbt/` запечены в образ. После пересборки образа под загрузчик (2026-11-22) dbt-модели добавились позже, и ручной прогон прошёл успешно с новой задачей extract (DAG смонтирован, extract запечён), но `dbt source freshness` проверил 3 источника вместо 6, а `dbt build` выдал `PASS=117 WARN=2 TOTAL=119` — граф без новой модели; следующий прогон после пересборки дал новые итоги. → После любой правки вне `dags/` пересобирать образ до прогона, который должен её доказать, и читать в логе задачи, что выполнено (число узлов и источников), а не только её статус.
95. **Ручной Drain может оставить просроченный плановый слот, который выполнится после Unpause.** DAG стоял на паузе примерно с 19:00 UTC (2026-11-22), следующий слот — 21:07. За Drain-прогоном в 21:26 (закончился в 21:28:53) последовал Unpause, и `scheduled__2026-11-22T21:07` стартовал в 21:30:39 (8 с, все задачи skipped: нового нет). Drain снимает паузу на время своего прогона, поэтому scheduler создал просроченный слот; тот подождал за ручным прогоном (`max_active_runs=1`) и выполнился, как только DAG стал активным. Пауза, за которую слот не прошёл (09:16–09:17 UTC 2026-11-24), лишнего прогона не оставила. → Здесь безвредно (полностью пропущенный прогон ничего не стоит); перед Unpause DAG, у которого лишний прогон стоил бы денег, — смотреть очередь его запусков.
98. **Umask, заданный в обёртке, наследует команда, а Docker Desktop хранит Linux-права на bind mount Windows.** `with-private-keys.sh` ставил `umask 077` для копий ключей и `exec`-ал команду с ним. Экспорт через сервис `project` (2026-11-24 09:14 UTC) записал каталог с правами `0700` и файлы `0600`, владелец uid 50000; на хосте Windows они выглядят как обычные файлы, а внутри другого контейнера (дашборд, uid 1000) не читаются («Permission denied»). Scheduler это не задело только потому, что `/entrypoint` Airflow после обёртки ставит `umask 0002` (его экспорты — `0775`). Docker Desktop хранит Linux-владельца и права файлов, записанных в bind mount Windows, и копия, сделанная в Windows, уносит их с собой. → Обёртка возвращает umask вызывающего перед `exec` (копии ключей остаются `0400`); проверять, что видит другой контейнер (`ls -l` внутри него), а не Проводник Windows.
103. **tmpfs без явного `mode` после перезапуска может вернуться с правами `755 root`.** После перезагрузки Windows (2026-11-25 ~12:43 UTC) `airflow-scheduler` оригинала крутился в `Restarting (1)`: `with-private-keys` падал с `mkdir: cannot create directory '/run/project-keys/50000': Permission denied`. Docker Engine 29.9.3 монтирует tmpfs без `mode` с правами `1777`, когда создаёт контейнер, а при перезапуске существующего tmpfs получает права точки монтирования — `/run/project-keys` в образе нет, и Docker создал его `755 root`. tmpfs `/tmp` дашборда остался `1777`: этот каталог в образе уже `1777`. С `--tmpfs /path:mode=1777` права пережили `docker restart` (проба). Восстановлено `up -d --force-recreate --no-deps airflow-scheduler`; исправлено в compose оригинала (`/run/project-keys:mode=1777`, коммит `e5f002b`). → tmpfs на каталоге, которого нет в образе, — с явным `mode`; проверять стек после перезагрузки машины, а не только после `up`.
104. **После перезагрузки Windows часы спешили относительно Binance.** 2026-11-25 ~12:58 UTC, после перезагрузки выше, хост спешил на +1.09 с относительно времени сервера Binance (три замера, RTT 0.52–0.55 с), контейнер — на +1.20 с; до перезагрузки часы отставали на 0.2–1.8 с (пп. 26, 80). `w32tm /query /status`: `Source: Local CMOS Clock`, `Leap Indicator: 3 (not synchronized)`, успешной синхронизации нет — служба времени работала, но с загрузки не синхронизировалась. Спешащие часы — то направление, о котором предупреждал п. 26 (незакрытая свеча выглядит закрытой); прогоны в :07 и лаг публикации 5 мин делают это безвредным для расписания. После `w32tm /resync /force` (администратор; синхронизация с `time.windows.com` в 13:24 UTC) хост показал −0.17 с, контейнер −0.05 с — VM Docker подтянулась за хостом без перезапуска. → После перезагрузки сверять часы с Binance, прежде чем доверять ручным прогонам около начала часа, и синхронизировать, если спешат.

## Наблюдения об инструментах: дашборд (DuckDB, Streamlit, Altair)

99. **Health check Streamlit проходит до первого запуска страницы, а headless-старт ходит наружу.** Streamlit 1.67 в контейнере дашборда (2026-11-24): `/_stcore/health` отвечал `ok`, хотя страница не могла открыть ни одного Parquet-файла: скрипт страницы запускается только на сессию браузера; `streamlit.testing.v1.AppTest` внутри того же read-only контейнера запустил скрипт и показал ошибку. Headless-старт узнаёт публичный IP машины у checkip.amazonaws.com, чтобы напечатать «External URL» (`bootstrap._print_url`), если `browser.serverAddress` не задан явно. Streamlit читает `~/.streamlit/secrets.toml` при первом запуске: tmpfs от root поверх домашнего каталога превратил это в `PermissionError`, а собственный домашний каталог образа на read-only корне работает. → Проверка контейнера запускает страницу (AppTest) на настоящем экспорте; в команде — `--browser.serverAddress=localhost`; tmpfs только `/tmp`.

100. **DuckDB 2.0 держит соединение занятым, пока результат не дочитан, а блокировка конфигурации сохраняет пояс.** В duckdb 2.0.1 `fetchone()` оставил результат незавершённым, и следующий оператор на том же соединении упал с `ResourceInUseException` («connection has an unfinished result»); `fetchall()` (или курсор на запрос) работает. В `.df()` DECIMAL приходит как float64, TIMESTAMPTZ — в `TimeZone` сессии (задан UTC). `SET enable_external_access = false` на работающей базе не отменить, но без `SET lock_configuration = true` другие настройки, включая `TimeZone`, менять можно. Повреждённый Parquet даёт `InvalidInputException`, а не `IOException`. → Дашборд загружает экспорт в базу в памяти, затем выключает доступ к файлам и блокирует конфигурацию; результаты читает `fetchall`/`df`, обе ошибки превращает в свою ошибку снимка.

101. **Vega-Lite рисует время в поясе зрителя.** Графики Altair с UTC-временем показали бы часы пампов и сборки dbt зрителю в UTC+1 на час позже, чем расписание, данные и run id Airflow; тики годовой временной оси по умолчанию недельные, и месячный формат повторял «Dec 2025» четыре раза. → Временные оси — `scale(type="utc")` с `tickCount="month"`; подсказки — готовые строки UTC.

## Наблюдения об инструментах: DuckDB и dbt-duckdb

105. **Настройки dbt-duckdb: единицы, потоки и каталог файла.** С dbt-core 1.12.7, dbt-duckdb 1.11.1 и duckdb 2.0.1 (2026-11-25) `dbt debug` подключается, а `settings` профиля доходят до сессии (`current_setting('TimeZone')` = `UTC`), но: `memory_limit: 1GB` — это 10^9 байт, показывается как `953.6 MiB` (`1GiB` даёт `1.0 GiB`); собственные `threads` DuckDB по умолчанию — все логические ядра (здесь 12), что бы ни было в `threads` dbt: у dbt это сколько моделей идёт одновременно, у DuckDB — сколько воркеров у каждого запроса; и DuckDB не создаёт каталог файла базы (`IO Error: Cannot open file`). → В профиле `memory_limit: 1GiB` и `threads: 4` в `settings` (до переключения два пайплайна делят VM Docker на 6 ГБ), а `warehouse/` держится в git с `.gitkeep`.
106. **Боковое соединение `read_text` и `json_each` не помещает годовой батч в 1 GiB.** Первый батч свечей (`20261120T194005Z`: 23 файла примерно по 1.6 МБ, по 8 759 свечей, 37 МБ JSON) упал с `Out of Memory Error ... (1023.1 MiB/1.0 GiB used)` при загрузке одним `INSERT ... SELECT ... FROM read_text(?) AS f, json_each(f.content) AS e` (DuckDB 2.0.1, `memory_limit` 1 GiB, 4 потока; с `md5(f.content)` и без, и с файлами в CTE). Один `INSERT ... FROM json_each(?::JSON)` на файл, с текстом файла параметром, загрузил те же 201 457 строк за 0.4 с. Полная пересборка RAW до последнего батча эталона заняла 36 с на 166 батчей (файл 20.7 МБ); все 60 точных raw-метрик равны эталону Snowflake. → Загрузчик читает каждый файл в Python (заодно проверяет число строк и хеширует байты) и вставляет его отдельным оператором, все файлы батча — в одной транзакции; тест грузит год свечей по четырём символам при лимите 64 МБ.
107. **`_file_content_key` в двух движках значит разное.** В Snowflake это `METADATA$FILE_CONTENT_KEY` — MD5 gzip-файла в stage (п. 23); в DuckDB stage нет, и загрузчик пишет md5 байтов файла, как его записал extract. Оба определяют точную версию файла, но между движками не сравниваются; эталон эту колонку не использует. Остальной lineage совпадает: `_source_file` — `<batch>/<SYMBOL>.json` (в Snowflake — `.json.gz`), `_file_row_number` — позиция записи в файле, с 1.
