# Source: Binance Spot API — klines

- Endpoint: `GET https://api.binance.com/api/v3/klines`
- Market data mirror: `https://data-api.binance.vision`
- Parameters: `symbol`, `interval`, `startTime`, `endTime`, `limit` (default 500, max 1000)
- Docs: https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints

## Data Quality observations

1. **The candle key is open_time.** Each candle covers `[open_time, open_time + 1h − 1ms]`; the next candle starts at `close_time + 1 ms`.
2. **The latest candle may still be open.** On 2026-11-19 at 17:22 UTC, the 17:00 candle showed a volume of 509 BTC vs ~1,200 for closed candles. Rule: load only candles with `close_time < now`.
3. **Prices and volumes are returned as strings** to preserve precision (quote_volume has up to 16 significant digits). Store as `NUMBER(38, 8)`; never cast to float.
4. **Timestamps are Unix epoch milliseconds in UTC.** Always pass `tz=timezone.utc` when converting in Python.
5. **Volume estimate:** one year of hourly candles ≈ 8,760 rows, i.e. at least 9 requests of 1,000 rows per symbol.
6. **A typo in a symbol may silently return another instrument.** `BTCUSD` (instead of `BTCUSDT`) returns valid data with a similar price (+0.2%) but ~16,000x lower volume. Mitigation: fixed symbol whitelist (`dim_symbol` + dbt `relationships` test) and a minimum liquidity threshold.

## Symbol selection (whitelist) observations

Script: `ingestion/select_symbols.py` → `config/symbols.csv` (future source for `dim_symbol`).

7. **Incomplete history for new listings.** A symbol listed 3 months ago has ~2,200 hourly candles instead of ~8,760 per year; in cross-symbol comparisons this looks like gaps. → Rule: `first_candle_date` at least 365 days ago.
8. **Ticker ≠ asset.** Renames split history across symbols: LUNA → LUNC after the Terra collapse (May 2022), so `LUNCUSDT` starts on 2022-09-09. `first_candle_date` is the ticker's listing date, not the asset's. → Never merge symbols by base asset name without a mapping table.
9. **Non-crypto instruments on the spot market.** Stablecoins (new ones appear constantly, e.g. RWUSD in Oct 2026), gold-backed tokens (PAXG, XAUT), tokenized stocks/ETFs (NVDAB, QQQB, MSTRB, …). → Explicit exclusion list + data rule: 30d close range within [0.98, 1.02] ⇒ USD-pegged, excluded. Open issue: tokenized stocks are currently excluded only by the history rule.
10. **24h volume is a noisy liquidity metric.** MMTUSDT: 52.6M 24h vs 2.3M 30d average (×22); LUNCUSDT ×9; SKYUSDT ×8. A single snapshot gave 3 false positives out of 24. → Rule: 30-day average daily quote volume ≥ 10M USDT.
11. **Whitelist is a snapshot.** Volumes change daily, so re-running the script changes the list. → `config/symbols.csv` is committed to git and regenerated only deliberately; `selected_at_utc` records when.

## API behaviour observations

12. **Error semantics.** Errors return a JSON body `{"code": ..., "msg": ...}`, e.g. `HTTP 400 {"code":-1121,"msg":"Invalid symbol."}`. 4xx = our mistake, never retried. 429 = rate limit, may include `Retry-After` (seconds). 418 = IP ban after ignoring 429s, never retried (retrying extends the ban). 5xx = transient, retried with exponential backoff. → Implemented in `ingestion/clients/binance.py`.
13. **Expected row count is 8,759, not 8,760.** `startTime` is not aligned to the hour, and Binance returns candles with `open_time >= startTime`, so the first candle is the next full hour; the current hour is dropped as unclosed. Verified on all 23 symbols: 8,759 rows, 0 duplicates, 0 gaps (as of 2026-11-19 18:31 UTC). Directly confirmed on 2026-11-20: for as-of 19:40:05 UTC (`startTime` = 2025-11-20 19:40:05) the first candle in RAW opens at 20:00:00, not at 19:00 (the candle containing `startTime`). → Row-count checks must expect 8,759 for a 365-day window computed from a single as-of timestamp.
14. **Without `startTime`, klines returns the most recent `limit` candles, and the last one is still open.** Checked on 2026-11-19 20:11 UTC: `BTCUSDT 1d limit=3` returned two closed days and today's candle with `close_time > now`. With `startTime=0, limit=1` the API returns the very first candle (BTCUSDT: 2017-08-17), i.e. the listing date. → `select_symbols.get_daily_stats` requests `limit = days + 1` and drops the last candle (`[:-1]`). Here `[:-1]` is correct, unlike paging by `startTime` (note #2), where full pages contain only closed candles. Caveat: if trading is halted, the last candle may already be closed, and `[:-1]` drops one good day.
26. **The local clock is not Binance's clock.** Five `GET /api/v3/time` calls on 2026-11-20 put the server 1.34 s ahead of the local clock (round trip ~250 ms). `drop_unclosed` and the batch id use the local clock: a local clock running *ahead* would treat a candle as closed up to that offset before its real close, while its volume is still changing. Here the offset is in the safe direction. → Incremental extract re-reads the newest extracted candle (`OVERLAP_CANDLES = 1`), so a candle taken too early is fetched again in final form by the next run, and staging keeps the version from the newest batch. Server time is not used as the as-of (one more request); revisit if the skew is ever on the unsafe side.
27. **Closed candles do not change.** The last 48 closed hourly candles of batch `20261120T194005Z` (extracted 40 minutes after the newest one closed) were compared with the live API about an hour later: 1,104 candles, 0 differences. After the first incremental load, the 23 seam candles present in both batches had identical payloads in RAW (`COUNT(DISTINCT TO_JSON(payload)) = 1` per candle). → A high-water-mark increment is enough, no CDC needed; the 1-candle overlap is cheap insurance, and the same RAW query is the revision detector to keep running.
28. **`startTime` boundaries and request cost.** `startTime` equal to a candle's `open_time` returns that candle first (inclusive); `startTime` in the future returns `[]`; `startTime` at the current hour returns only the open candle. `GET /api/v3/klines` has weight 2 regardless of `limit`; `exchangeInfo` reports a `REQUEST_WEIGHT` limit of 6,000 per minute, and `X-MBX-USED-WEIGHT-1M` shows the weight used (2026-11-20). → The increment starts exactly at the high-water mark to re-read that candle; a symbol whose mark is already the newest closed candle is skipped without a request, so a run with nothing new costs 0 weight instead of 46 (23 × 2).
51. **A rise of +20 % in an hour almost never happens to liquid coins.** Over the year of the 23 whitelisted symbols (201,894 hourly close-to-close returns; the landing zone and Snowsight agree to the row, 2026-11-21): p99 = +2.70 %, p99.9 = +5.35 %, p99.99 = +9.26 %, maximum +20.44 % (INJUSDT, 2026-02-19 01:00), the only hour at or above 20 %. At or above 15 %: 4 hours; 10 %: 14; 5 %: 254 hours on 21 symbols (BTCUSDT peaks at +4.08 %). Neighbouring hours of one move (WLDUSDT 2026-01-28 21:00 +19.4 % and 22:00 +15.2 %) collapse to 189 episodes with a 24 h cooldown. On 2026-11-15 02:00 nine symbols rose 5 % or more in the same hour: a market move, not one coin's pump. Open interest history (from 2026-10-22, note 36) gives a full ±24 h window to 14 of the 189 episodes. → The pump threshold is 5 % (a dbt var); market breadth and the return z-score are kept in the mart, and conclusions about open interest state the sample size. +20 % pumps belong to the illiquid coins the whitelist excludes.
52. **Hourly volume has a heavy right tail.** A z-score of `quote_volume` against the trailing 168 hours exceeds 5 in 1,774 hours of the year, on all 23 symbols; a z-score of `ln(quote_volume)` exceeds 5 in 24 hours, on 14 symbols. No hour has zero volume. → The anomalous-volume warn uses the logarithm; mutation R6 (raw volume) turns its 24 rows into 1,774.

## API observations: Binance USD-M Futures

Endpoints of `https://fapi.binance.com` used for funding rate and open interest, probed live on 2026-11-20/21 for the 23 whitelisted coins.

30. **Access and rate limits.** `fapi.binance.com` answers from Montenegro without a VPN; the local clock was 1.77 s behind the futures server (the safe direction, as in note 26). `exchangeInfo` reports a `REQUEST_WEIGHT` limit of 2,400 per minute (spot: 6,000). Funding history shares a separate limit of 500 requests per 5 minutes with `fundingInfo`; open interest history has 1,000 requests per 5 minutes. These two endpoints return no `X-MBX-USED-WEIGHT` header, so their usage cannot be read back. → A first run is about 50 funding and 46 open interest requests, an hourly run about 23 open interest requests and no funding requests between settlements; extracts pause 0.2 s between pages.
31. **Spot symbol ≠ futures symbol; substrings lie.** 22 of the 23 coins have a USD-M perpetual under the same symbol; `PEPEUSDT` maps to `1000PEPEUSDT` (`baseAsset` `1000PEPE`, quoted per 1,000 coins). Matching on a substring of the symbol finds wrong contracts: `BTCDOMUSDT` (a BTC dominance index), `PUMPBTCUSDT` (another coin, status `SETTLING`), `ETHFIUSDT`, `ETHWUSDT`. Quarterly contracts share the `baseAsset` (`BTCUSDT_261225`), and `contractType` `TRADIFI_PERPETUAL` marks tokenized stocks (`OPENAIUSDT`, `UNITREEUSDT`), an explicit flag the spot `exchangeInfo` lacks (note 9). → `map_perpetuals` matches `baseAsset` (optionally prefixed `1000`, `1000000` or `1M`), `contractType = PERPETUAL`, `status = TRADING`, quote USDT, and keeps the multiplier in `config/perpetuals.csv`; two candidates for one coin stop the mapping.
32. **Funding history: inclusive `startTime`, first `limit`, and `startTime=0` means "not sent".** `startTime` equal to a record's `fundingTime` returns that record first, to the millisecond; with a range wider than `limit` (max 1,000) the first `limit` records come back, ascending; a future `startTime` returns `[]`. `startTime=0` is taken as absent and returns the most recent records, not the oldest (for spot klines it returns the listing date, note 14). BTCUSDT history starts on 2019-09-10; old records have `markPrice` `""` (empty string), records of the last year all have a value; `rateType` is `Regular` (the docs reserve `Special` for stock dividends). → Paging goes forward from the last `fundingTime + 1`; the client refuses `start_time <= 0`; staging must treat an empty `markPrice` as NULL, not cast it.
33. **`fundingTime` lands a few milliseconds after the hour.** Over a year of BTCUSDT settlements, 461 of 1,000 sit exactly on the hour, the rest 1 to 26 ms later (`00:00:00.007`). → The grid key is the hour (`fundingTime // 1 h`): the extract's duplicate and gap checks, the loader's duplicate count in RAW (`FLOOR(fundingTime / 3600000)`) and staging use the same key.
34. **The funding interval differs per contract and changes over time.** 19 of the 23 contracts settle every 8 h, ENA, PUMP, TAO and ASTER every 4 h (grid aligned to 00:00 UTC). `fundingInfo` lists only contracts whose cap, floor or interval was adjusted (833 of 956); `GTCUSDT` is 4 h there now but settled every 8 h in June 2026. The API serves no interval history. → The extract takes the current interval (8 h when not listed) and records it per file (`interval_hours`); `expected` is an estimate, so a mismatch is a DQ warning, not a stop.
35. **The platform skips settlements.** The 2026-06-24 04:00 settlement is missing for 20 of the 21 contracts checked that settled every 4 h that day (ENA, PUMP, TAO, ASTER, LPTUSDT, KERNELUSDT and others); only IRYSUSDT has it. 8 h contracts have no settlement at that hour. The first full-year extract therefore shows `rows=2189, expected=2190, gaps=1` for the four 4 h contracts. → A real source gap caught by the DQ check: report it, flag it in staging, do not interpolate.
36. **Open interest history covers about one month, and older times are an error.** `openInterestHist` serves a rolling 744 hourly points (~31 days); a `startTime` or `endTime` older than that is `HTTP 400 {"code":-1130,"msg":"parameter 'startTime' is invalid."}`, not an empty answer (and 4xx is not retried). The docs give `limit` max 500, yet 501 and 1,000 are accepted (1,000 returned all 744 points). Timestamps sit exactly on the hour; per the docs, a period without trades has no point. → RAW is the only copy of older open interest, so the extract must run at least every 30 days; it asks for 30 days at most (a day's margin off the rolling edge), reports points that fell out of the window as `lost`, and keeps `limit` at the documented 500.
37. **Open interest pages the opposite way: the LAST `limit` points.** With `startTime` alone, or `startTime` and `endTime` spanning more than `limit` points, the newest `limit` points of the range come back; klines and funding return the oldest. Paging forward by `startTime` like klines would return the newest 500 of 720 points and silently drop the first 220. → Pages are explicit windows of at most 500 hours (`startTime` to `startTime + 499 h` as `endTime`): a window no wider than `limit` comes back whole. Two windows give the 720 points of 30 days with no duplicates.
38. **Open interest point T is published about a minute after T and does not change.** Polling around 22:00 UTC on 2026-11-20, the 22:00 point appeared 61-76 s after the hour; it and the three previous points kept identical values over the next 7 and 20 minutes. The docs describe `timestamp` as the end of the period. → A point is expected 5 minutes after its time (`PUBLISH_LAG_MS`), otherwise a run at the top of the hour would report a false "no new points"; the high-water mark is enough, and the one-point overlap proves the seam. The funding publication delay is not measured yet; the same 5-minute lag is assumed.
39. **Funding sits on the interest rate most of the time: a repeated value is the formula, not stuck data.** Binance's FAQ (updated 2026-03-06) gives `F = [P + clamp(I - P, 0.05%, -0.05%)] / (8 / N)` with the interest rate `I` = 0.01 % per 8 h for most symbols: while the premium index stays between -0.04 % and 0.06 %, `F` equals `I`. In RAW (2025-11-21 to 2026-11-21), the maximum rate is exactly `0.00010000` for 12 of the 19 contracts on 8 h, and `0.00005000` (0.01 % / (8 / 4)) for 2 of the 4 on 4 h; minimums go far below (INJUSDT -0.01183133, TAOUSDT -0.00359598). All rates are JSON strings (`VARCHAR` in `VARIANT`) and cast exactly to `NUMBER(38, 8)`. → A "value did not change for N periods" DQ check would fire on healthy funding data; compare funding with `I / (8 / interval_hours)`, not with the previous value, and remember the 4 h contracts' rate is per 4 h when comparing contracts.
41. **The interest rate is per contract: BNBUSDT has none.** Live `GET /fapi/v1/premiumIndex` (2026-11-21, no symbol: every contract in one request) gives `interestRate = 0.00000000` for BNBUSDT and `0.00010000` for the other 22 contracts, the 4 h ones included: the rate is quoted per 8 h, and a 4 h settlement pays `0.0001 / (8 / 4) = 0.00005`. The modal BNBUSDT funding rate over the year in RAW is exactly 0 (55 % of settlements): with `I = 0` and a calm premium the formula of note 39 pays nothing. Spot against futures over the same year: the spot close of the candle ending at each settlement and the mark price per coin (`markPrice` / multiplier) never differed by more than 0.87 % (TRXUSDT); no record of the window has an empty `markPrice`. → `config/perpetuals.csv` keeps `interest_rate_8h` per contract (a snapshot: no history is served), and the staging check compares each contract's modal funding rate with its own `interest_rate_8h * interval_hours / 8`. A check with the FAQ's constant 0.01 % flags BNBUSDT on healthy data (mutation Q7: exactly that one row).
81. **The long/short ratio endpoints keep 30 days, like open interest.** A live probe (2026-11-22, BTCUSDT, `period=1h`): `topLongShortAccountRatio`, `topLongShortPositionRatio`, `globalLongShortAccountRatio` and `takerlongshortRatio` (all under `/futures/data/`) answer a window that starts 29 or 30 days back and refuse 31 and 32 days with HTTP 400 `-1130` "parameter 'startTime' is invalid", the same rolling limit as `openInterestHist` (note 36). `takerlongshortRatio` returns no `symbol` (only `buySellRatio`, `buyVol`, `sellVol`, `timestamp`), and its newest point was an hour older than the other three at the same moment. → A fourth dataset follows the open interest template (windows with `endTime`, the symbol from the file name) with its own publication lag to measure; each day it is postponed loses one day at the start of its history, not all of it.
89. **Three long/short endpoints are snapshots; the taker one is an hour of volume stamped at its start.** Live probe (2026-11-22): the points of `topLongShortAccountRatio`, `topLongShortPositionRatio` and `globalLongShortAccountRatio` are on the hour and the newest one is the hour just ended, like open interest: a snapshot at `timestamp`. `takerlongshortRatio` at `timestamp = T` matches the taker buy and sell volume of the futures 1h candle that opens at T (`/fapi/v1/klines` fields 9 and 5 minus 9), a few units lower (up to 0.02 %: 4343.273 against 4343.895 BTC), and its window filter goes by the period end (a `startTime` of 18:22 returned the point stamped 18:00). The "newest point an hour older" of note 81 is this, not a publication lag. → The three ratios are extracted (each its own RAW table: the payloads have the same shape, so only the table tells the series); the taker endpoint is left out, since futures klines keep the same volume for years, not 30 days.
90. **Paging and limits are those of open interest.** All four endpoints return the LAST `limit` points of `[startTime, endTime]` (both inclusive), refuse a 31-day-old `startTime` with HTTP 400 `-1130`, and answer without `X-MBX-USED-WEIGHT` headers (documented: IP weight 0, an own limit of 1000 requests per 5 minutes). `limit=1000` was accepted although 500 is the documented maximum (it returned all 720 points of the window). All 23 contracts had 720 hourly points in each endpoint, without a gap. → One extract algorithm for every /futures/data/ series (`futures_stats.py`, windows of 500 h with `endTime`); open interest became one of its configurations.
91. **Shares come rounded, the ratio does not: a fixed tolerance fails at high ratios.** `longAccount` and `shortAccount` carry 4 decimals and always sum to 1; `longShortRatio` is long / short of the unrounded shares. A check `|ratio - long/short| <= 0.0006` flagged 963 of 16 560 rows of `topLongShortPositionRatio` (ratios up to 5.5, short shares down to 0.15: the error of a rounded share grows with 1/short); the bounds the rounding allows, `(long ∓ 0.00005) / (short ± 0.00005) ∓ 0.00005`, flag none of 48 024 rows of the three series. Medians over the 23 contracts and 30 days: all accounts 1.70, top accounts 2.11, top positions 1.92. → Stop-level tests in staging: shares in [0, 1] summing to 1 within 0.0001, and the ratio within the rounding bounds. Swapped share columns pass the first and only the second stops them (mutant E2: 49 674 of 49 680 rows; the other 6 are hours at exactly 0.5 / 0.5).
92. **Every /futures/data/ point was out within three minutes and did not change.** Polling every 5 s around 2026-11-22 19:00 UTC (BTCUSDT): `topLongShortAccountRatio` served the 19:00 point after 33 s, `takerlongshortRatio` its 18:00 point after 84 s, `globalLongShortAccountRatio` after 132 s, `openInterestHist` after 137 s (61-76 s on 2026-11-20) and `topLongShortPositionRatio` after 164 s; by 19:04 every contract had the new point in every endpoint. A minute later the first-seen points were the same, and the 696 points also present in a snapshot taken at 18:25 had not changed. → The 5-minute publication lag and the :07 schedule hold for the new series; the lag of one endpoint varies from day to day, so it is not tuned tighter.

## Platform observations: Snowflake

Trial account created 2026-11-20 (Standard edition, `AWS_US_EAST_2`). Setup script: `snowflake/setup.sql`.

15. **The role you pick is not the only role in effect.** Users get `DEFAULT_SECONDARY_ROLES = ('ALL')` by default, so every role granted to the user also authorizes statements. Under `CRYPTO_DWH_ROLE`, which has no `OWNERSHIP` on schemas, `DROP SCHEMA CRYPTO_DWH.RAW` succeeded; `ACCOUNT_USAGE.QUERY_HISTORY` shows `secondary_role_stats = {"roleCount":4,...}` for that statement. After `USE SECONDARY ROLES NONE` it fails with "Insufficient privileges ... must have OWNERSHIP". Snowsight also runs `USE SECONDARY ROLES ALL` in its own sessions; a worksheet keeps one session across runs, and `USE ROLE` does not reset secondary roles. → Least privilege must come from the roles granted to the user: the loader gets a dedicated service user with only the project role. Negative grant tests run with secondary roles off, otherwise they test the user, not the role.
16. **"Does not exist or not authorized" means either one.** `CREATE TABLE` in a dropped schema and `USE WAREHOUSE` without `USAGE` return the same kind of error: Snowflake does not reveal whether an object exists to a role that cannot see it. → When debugging, check existence as an admin role before suspecting grants (and the reverse).
17. **New trial accounts come with warehouses that idle for 5 minutes.** The signup form assigned the cloud region and edition without asking. Snowflake pre-provisioned `COMPUTE_WH` (the user's default) and `SNOWFLAKE_LEARNING_WH` with `AUTO_SUSPEND = 300`, plus `SYSTEM$STREAMLIT_NOTEBOOK_WH` with 60; all X-Small, Gen2 (`STANDARD_GEN_2`), owned by `ACCOUNTADMIN`. Gen2 is the default for new warehouses and costs 1.35x Gen1 credits on AWS; `STATEMENT_TIMEOUT_IN_SECONDS` defaults to 2 days. → `setup.sql` creates the project warehouse with explicit `GENERATION = '1'`, `AUTO_SUSPEND = 60`, a 600 s timeout, and applies the same idle and timeout limits to the pre-provisioned warehouses.
18. **Metadata statements do not wake the warehouse; `updated_on` is not a change log.** `USE`, `SHOW`, `CREATE`/`DROP TABLE` and context functions ran with `CRYPTO_WH` suspended (`resumed_on` stayed at the last real query). `updated_on` moved on a no-op `ALTER ... SET` with unchanged values and on every resume. → Count credits from warehouse metering, not from statement counts; track configuration drift by comparing properties with `setup.sql`, not by `updated_on`.
19. **A trial grants a role to PUBLIC, i.e. to every user.** Account provisioning grants `SNOWFLAKE_LEARNING_ROLE` to `PUBLIC`: `USAGE`/`OPERATE` on `SNOWFLAKE_LEARNING_WH` (Gen2, not under the project warehouse's daily monitor) and `CREATE SCHEMA` in `SNOWFLAKE_LEARNING_DB`. The service user `CRYPTO_LOADER`, granted only the project role, could still use it: `SHOW GRANTS TO USER` showed one role, while `CURRENT_AVAILABLE_ROLES()` in the smoke check returned three. → Check effective roles, not direct grants. `setup.sql` grants the role to the admin user and revokes it from `PUBLIC`; adding it to the expected roles would have legitimised the leak.
20. **A wrong key passphrase looks like a server-side rejection.** With the public key pasted into `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` by mistake, connector 5.2.0 raised `250001 (08001): Failed to login: Authentication failed. Unspecified`, yet `LOGIN_HISTORY_BY_USER` recorded no attempt (the next, successful login was recorded with `RSA_KEYPAIR`). The failure was apparently on the client, since the key could not be decrypted, but the message says otherwise. → On "Authentication failed", check the login history first: no record means a client-side problem (passphrase, key file); a record carries the server's `error_message`.
21. **COPY skips a file it loaded before only while the file is unchanged, and says so per file.** Load metadata is kept per table for 64 days (file name, size, ETag, rows). `FORCE` is described as loading files "regardless of whether they were loaded previously and haven't changed", so a changed file under the same name loads again. Repeating `COPY ... FILES = ('BTCUSDT.json.gz')` for a loaded file returned one row: `status = LOAD_SKIPPED`, `errors_seen = 1`, `first_error = "File was loaded before."`, and the table did not change. It did not return "Copy executed with 0 files processed." (2026-11-20). → Extract writes immutable batch directories (`<batch_id>/<SYMBOL>.json`), so a file never changes under a loaded name; the loader treats `LOAD_SKIPPED` as a stop that needs a human decision (`TRUNCATE` clears the load metadata, `FORCE` ignores it).
22. **PUT reports `SKIPPED` for a different file under an existing name, and keeps the old one.** With `OVERWRITE = FALSE`, connector 5.2.0: PUT of a new file → `UPLOADED`; the same file again → `SKIPPED`; a file with the same name and new content → also `SKIPPED`, with an empty `message`, and `LIST` still shows the original size and MD5 (experiment in a separate stage directory, 2026-11-20). The two cases cannot be told apart from the PUT result. → A batch directory is never rewritten (extract fails if it exists). Known limit: if a staged batch were edited locally (manifest included) and re-run, COPY would load the old staged version; only a changed row count would be caught by reconciliation. Comparing local and staged MD5 does not work: gzip output differs between compressors (header timestamp, settings).
23. **File metadata in COPY: relative path, MD5, element number.** `METADATA$FILENAME` is the path inside the stage (`20261120T194005Z/BTCUSDT.json.gz`), while `LIST` and the COPY result prefix the stage name (`klines_stage/20261120T194005Z/...`). `METADATA$FILE_CONTENT_KEY` equals the MD5 that `LIST` shows for the staged (compressed) file. With `STRIP_OUTER_ARRAY = TRUE`, `METADATA$FILE_ROW_NUMBER` is the 1-based position of the array element, in file order (1..8,759, `LAG` over it finds no out-of-order rows). → Parse paths from the end (`SPLIT_PART(..., -1)`), not by a fixed prefix; `_file_content_key` identifies the exact file version a row came from.
24. **`TIMESTAMP_LTZ` output follows the session time zone, which defaults to US Pacific.** `COPY_HISTORY.LAST_LOAD_TIME` and `created_on` in `SHOW` output came back as `-0800`, consistent with the default session time zone `America/Los_Angeles`. → Stored timestamps are converted explicitly: `_loaded_at = CONVERT_TIMEZONE('UTC', METADATA$START_SCAN_TIME)` (2-argument form returns `TIMESTAMP_TZ`), so RAW reads the same from any session (note #4).
25. **JSON strings stay strings in `VARIANT`.** Binance sends prices as JSON strings; in RAW `TYPEOF(payload[1])` is `VARCHAR` and `payload[1]::NUMBER(38, 8)` gives the exact decimal (`"86921.27000000"` → `86921.27000000`), while `open_time` is `INTEGER`. → Cast prices to `NUMBER(38, 8)` in staging, never through `FLOAT`/`TO_DOUBLE` (note #3).
29. **`QUERY_HISTORY` shows which statements used the warehouse: look at `WAREHOUSE_SIZE`, not `WAREHOUSE_NAME`.** For `CRYPTO_LOADER` (`INFORMATION_SCHEMA.QUERY_HISTORY_BY_USER`, 2026-11-20), every statement had `WAREHOUSE_NAME = CRYPTO_WH` (the session's current warehouse), but `WAREHOUSE_SIZE` was filled only for `SELECT DISTINCT _batch_id`, the batch statistics `SELECT` and `COPY`. It was empty for the DDL (`CREATE ... IF NOT EXISTS`, `ALTER ... SET`), `PUT` and the context-function `SELECT` of the smoke check. A loader run with nothing to load ran one warehouse statement (`SELECT DISTINCT`, 180 ms); it came 18 s after the previous run and found the warehouse still running. 53. **ASOF JOIN answers "the last settlement at or before the hour".** `ASOF JOIN funding MATCH_CONDITION (hours.hour_end_ms >= funding.funding_hour_ms) ON hours.symbol = funding.spot_symbol` returns at most one right row per left row and null-pads a left row without a match, like a left join. Per the docs (read 2026-11-21) the match condition takes `>=`, `<=`, `>` or `<` on timestamps or numbers, ties on the right side are resolved non-deterministically, and the examples chain an INNER or another ASOF join after it, never an outer join. dbt Core 1.12.7 with dbt-snowflake 1.12.5 on Python 3.12, Windows, run from the repo root as the service user `CRYPTO_DBT`.

46. **dbt-snowflake 1.12.5 passes connector 4.x parameters to connector 5.2.0.** Every new session prints `UserWarning: Unknown parameter 'insecure_mode'` (also `reuse_connections`, `ocsp_root_certs_dict_lock_timeout`) and the connector's `FutureWarning` about `enable_server_session_keep_alive_auto_detection`, which a dbt profile cannot set; with 4 threads a run prints them up to six times. Compatible by version range is not the same as tested with this version.
47. **dbt 1.12 loads `.env` itself, searching upward from the working directory.** `dbt/cli/main.py` calls `load_dotenv(find_dotenv(usecwd=True), override=False)` before parsing arguments, so `DBT_PROJECT_DIR=dbt` and `DBT_PROFILES_DIR=dbt` in the repo-root `.env` let every dbt command run from the repo root; shell variables win over the file, and for a key listed twice python-dotenv takes the last occurrence (the repo's `.env` had two `SNOWFLAKE_ACCOUNT` lines with different values, and the loader used the second). `private_key_path` is opened as given: `~` is not expanded, unlike the loader's `connection_params`. 50. **At this size an incremental merge was slower than a full rebuild, and produced the same table.** `stg_binance__klines_1h` on 2026-11-21, 201,917 → 201,940 rows, one new batch of 23 symbols × 2 candles (`QUERY_HISTORY_BY_USER`, `CRYPTO_DBT`). Revisit when a rebuild takes minutes: then merge with `incremental_predicates` or clustering to prune the target, and keep the `hash_agg` comparison with a rebuild as the correctness check.
55. **`store_failures` replaces, it does not accumulate.** The test materialization of dbt-core 1.12.7 drops the previous relation, creates a table or view from the test query, then counts the failures with `select count(*)` from what it stored. Without a schema config the relation goes to `dbt_test__audit`, passed to `generate_schema_name` like any custom schema; a test name of 64 characters or more becomes a hashed alias (`DBT_UTILS_EXPRESSION_IS_TRUE_S_1077…`). `limit` is applied before both the store and the count, so the failure count is capped too. Unit tests do not store failures. A stored warn or fail prints `See test failures: select * from CRYPTO_DWH.DQ.<alias>`. → Findings of every run live in DQ (warn tests as tables with readable aliases, stop tests as views), their history in a log written by a hook; no `limit`.
56. **What `results` in `on-run-end` holds, checked on a live run.** One result per executed node, hooks excluded: `status` (`pass`/`warn`/`fail`/`error`/`skipped` for tests, `success` for models), `failures` (NULL for models and skipped tests), `execution_time`, `timing` (naive UTC), `message`, and the node. The configured severity is raw: `ERROR` (the default of `TestConfig`) or `warn` as written in YAML. A generic test has `attached_node` and `column_name`, a singular test has neither (only `depends_on.nodes`), a unit test names its model in `tested_node_unique_id`, a seed depends on macros only. Statuses and severities are `str` subclasses; connector 5.2 binds them as strings. `adapter.add_query(sql, bindings=...)` is callable from Jinja (seeds use it) and Snowflake connections autocommit. In dbt 1.12 the project hooks are counted in the totals (`Finished running 2 project hooks`, `PASS=109` for 109 nodes plus 2 hooks), a failing hook is an ERROR and a non-zero exit, and `dbt source freshness` runs them as well (`source_freshness_run_project_hooks` defaults to true). → The log macro casts every value to plain `str`, guards the attributes a node type lacks, lowers severity in the view, and subtracts the two hooks when comparing totals with the log.

The long syntax with `uid`, `gid` and `mode` passes `docker compose config` and is then ignored, with a warning per field: "mode is not supported outside Swarm mode and will be ignored". A bind-mounted directory (`./data`) shows as `root:root 777` and is writable by uid 50000; files written from the container belong to the Windows user on the host. `docker compose config` prints the file with every `${...}` filled in, secrets included; `--quiet` validates without output. `${VAR:?message}` stops every compose command with that message when the variable is missing. → Keys get owner-only copies inside the container (note 60), the keys directory is a required variable, and compose is validated only with `--quiet`.
65. **Container clock and network.** The clock in a container equals the host's within 5 ms (both 0.91 s behind `api.binance.com` and `fapi.binance.com` on 2026-11-21, with the Windows Time service on the host stopped): Docker Desktop keeps the VM clock in step with Windows. From a container both Binance APIs and the Snowflake account endpoint (TLS 1.3, 0.5 s) are reachable without a VPN, as from the host. → The extract's as-of time and `drop_unclosed` behave the same in the container, and the one-candle overlap still covers a clock that runs ahead (note 26). Recheck after the machine sleeps, the known WSL 2 drift case.
66. **Lint and type checks depend on files around the code.** ruff 0.17 formats Markdown as well as Python, and reads `.gitignore` files from disk even outside a git checkout: in the image, which has no root `.gitignore`, `ruff format --check` covered 44 files (30 `.py` and 14 `.md` of `dbt_utils`) against 33 on the host (30 `.py`, `README.md` and the two source notes). pyright, told `venvPath = "."` and `venv = ".venv"`, found no `.venv` in the image and resolved imports with the first `python` on `PATH`, which is Airflow's venv without pytest: 14 errors. → `extend-exclude = ["dbt/dbt_packages"]` in `pyproject.toml` and a `.venv` link to the project venv in the test stage; then pytest (230 passed, 1 xfailed), ruff and pyright give the same results in Linux as on Windows. Compare the set of files a check covers, not only its verdict.
67. **The landing zone mounted from the host keeps the extract's high-water marks.** With `./data` bind-mounted, `high_water_marks` in the container returned the same 23 marks per dataset as on the host; reading the klines landing zone (with the old full-year batch) took 0.64 s against 0.30 s on the host. The live extract from the container continued from the host's mark (23 × 2 candles, batch `20261121T200350Z`) and `load_raw` from the container loaded and reconciled it. Manifests written on Windows contain CRLF (`Path.write_text`), those written in the container LF: harmless, since a manifest is parsed as JSON and never loaded into Snowflake. With an allow-list `.dockerignore` the build context is 300 kB although `.env`, `.venv` and `data/` (77 MB) sit in the repo. → `data/` stays a bind mount, never a named volume; if a manifest is ever compared byte for byte, write it with `newline="\n"`.
68. **The image's own init steps cannot fail.** In `/entrypoint` of `apache/airflow:3.4.0`, `_AIRFLOW_DB_MIGRATE` runs `airflow db migrate || true` and `_AIRFLOW_WWW_USER_CREATE` runs `airflow users create ... || true` (only when the auth manager is FAB). With a wrong database password that mechanism logged six "password authentication failed" errors and exited 0, so `service_completed_successfully` would have let the other components start on an unmigrated database. With no command and `_AIRFLOW_DB_MIGRATE=true` the entrypoint exits 0 after these steps. → `airflow-init` runs `airflow db migrate`, `airflow users create` and `airflow version` under `set -euo pipefail` (exit 1 on the same mutation); `users create` leaves an existing user as it is ("admin already exists in the db", exit 0), so the password in `.env` applies only on creation.
69. **Without a shared `airflow.cfg` every container generates its own secrets.** The official compose mounts one `./config/airflow.cfg` into all containers. Without it, each container writes its own file on first start (`write_default_airflow_configuration_if_needed` in `configuration.py`, mode 0600): a random `[api_auth] jwt_secret`, a random `[api] secret_key`, and a random `fernet_key` when none is set. The documentation of `jwt_secret` says it "must be consistent across all components that generate or validate JWT tokens (Scheduler, API Server)" and recommends passing it through the environment. → The Fernet key, the JWT secret and the API secret key come from `.env` as `AIRFLOW__*` variables, required with `${VAR:?}`, like the postgres and admin passwords.
70. **`docker compose exec` does not see what the entrypoint exported.** `exec` starts a new process with the environment of the container's configuration, bypassing the entrypoint: in the scheduler it shows `SNOWFLAKE_PRIVATE_KEY_PATH=/run/secrets/...` (the 0777 mount), while the scheduler process itself (`/proc/7/environ`) has the owner-only copies made by `with-private-keys`. The LocalExecutor worker processes inherit them, but their `/proc/<pid>/environ` is overwritten by `setproctitle` and cannot be read; the image has no `ps` or `pgrep`. The smoke DAG's task reported both keys `ok` (owner-only), and the same check run in the scheduler container past the wrapper failed with "owned by uid 0". → What a task sees is checked by a task (`check_environment` in `smoke_environment`), not by `exec`.
71. **Airflow 3.4 details that tutorials get wrong.** `DagBag` lives in `airflow.dag_processing.dagbag` and has no `include_examples` (examples are only the `load_examples` setting); a DAG with `schedule=None` has a `NullTimetable` without `summary`, so a test checks `dag.schedule is None`. Triggering a paused DAG from the UI asks Unpause / Drain / Keep paused: Drain runs the trigger and pauses the DAG again when the run finishes (checked: `is_paused = True` after the run). `/api/v2/monitor/health` returns HTTP 200 with `triggerer: unhealthy` when no triggerer runs, so the healthcheck proves only that the API server answers. `BashOperator` pushes the last line of stdout to XCom by default ("Pushing xcom" in every task log), that is, into the metadata database. → Signatures are taken from the image (`inspect.signature`); manual runs of a scheduled DAG use Drain; tasks whose output is not needed get `do_xcom_push=False` (4.3).
72. **The LocalExecutor stack: footprint and exposure.** Postgres 50–80 MB, API server 280–320 MB (`[api] workers = 1`), DAG processor 180–240 MB, scheduler 370–440 MB: about 0.9–1.05 GB of the 6 GB VM. The API server and the DAG processor get only Airflow settings (no Snowflake variables, no `/run/secrets`, no `data/`); the scheduler gets the project's 12 variables, both key secrets and `data/` (writable), `dags/` read-only. The UI is published on `127.0.0.1:8080`: the machine's LAN address refuses the connection; the API answers 401 without a token or with a wrong password (FAB token endpoint `/auth/token`). → The LocalExecutor stack fits the machine with room for builds; Celery would add Redis, a worker and Flower.
73. **One build ran on an unregistered BuildKit container.** On 2026-11-21 one `docker compose build project` from the VS Code terminal printed "booting buildkit", pulled `moby/buildkit:buildx-stable-1`, downloaded the Airflow base image again, exported an OCI tarball and imported it (246 s), leaving a privileged container `buildx_buildkit_default` (946 MB of RAM while idle) with a 3.6 GB state volume. `docker buildx ls` listed only the `docker`-driver builders (`default`, `desktop-linux*`), the user's buildx instances directory was empty, the environment had no Docker or buildx variables, and the build was absent from the history of `desktop-linux`; repeated compose and plain builds went through `desktop-linux` (1–2.6 s, "unpacking to"). Not reproduced. → The container and volume were removed; a build that again shows "booting buildkit" or "sending tarball" is rerun with `--progress plain` to see who chose the builder.
74. **A secret scanner flags compose substitutions.** GitGuardian reported a "Generic Password" for the commit adding the Airflow services: the lines `postgresql+psycopg://airflow:${AIRFLOW_POSTGRES_PASSWORD:?...}@postgres/airflow`, `POSTGRES_PASSWORD: ${...}` and `--password "$${AIRFLOW_ADMIN_PASSWORD}"` match its patterns, although the values come from the gitignored `.env`. A script compared every value in `.env` with `git log -p --all` (and the pre-amend commit) and printed names only: no secret value occurs in the history. → Marked as a false positive; the code is not reshaped for the scanner. A secret is rotated when its value actually leaked (screenshot, chat, git), not on a pattern match.
77. **Exit code 99 is BashOperator's way to say "skipped".** In Airflow 3.4.0 (standard provider) `BashOperator` has `skip_on_exit_code=99` by default: exit 99 raises `AirflowSkipException`, any other non-zero code fails the task. The default applies to every BashOperator, so a command that exits 99 by accident would skip instead of fail; `skip_on_exit_code=None` turns it off. With the extracts ending 99 when they write no batch and `load_raw` on `trigger_rule=none_failed_min_one_success`, live runs behaved as designed: one or two extracts skipped and the load ran; all three skipped and everything downstream was skipped without starting (no task log at all), the run was a success in 8.9 s and Snowflake saw no session. On a schedule all three skip rarely: a new closed candle exists every hour. → Only the extracts may skip (`skip_on_exit_code=None` elsewhere, mutant P6); the exit code is the contract, not the printed text.
78. **Airflow 3.4 scheduling defaults.** Read from the image (2026-11-22): `catchup_by_default = False`, `create_cron_data_intervals = False` (a cron string becomes a `CronTriggerTimetable`: runs at the cron time, no data interval), `default_task_retries = 0`, `max_active_runs_per_dag = 16`, `default_timezone = utc`. `start_date` is optional; `catchup=True` without it fails at import, so the DAG does not load at all (mutant P2 was killed by the import test). The timetable has `run_immediately=False`: unpausing at 11:25 UTC did not run the missed 09:07 slot, the first scheduled run came at 12:07 (`scheduled__2026-11-22T12:07:00+00:00`). `airflow.sdk.CronTriggerTimetable` and `airflow.timetables.trigger.CronTriggerTimetable` are different classes; a DAG from `DagBag` has the SDK one. Task processes inherit the scheduler's environment (`os.environ.copy()` when `env` is not given), so they see the owner-only key copies of `with-private-keys`. → `max_active_runs=1` set explicitly; no `start_date`, because the extracts work from high-water marks, not dates.
79. **Cosmos and Airflow 3.4.** `astronomer-cosmos` 1.16.0 (released 2026-11-03, requires `apache-airflow>=2.11.0`) lists Airflow 3.4 among supported versions, but its table of tested runtimes ends at Airflow 3.3, and Cosmos 1.6–1.13 crashed Airflow 3.2/3.3 processes at startup with a circular import (compatibility policy, checked 2026-11-22). Cosmos would install into Airflow's own environment and render each model and test as a task, that is, one dbt invocation per node: about 119 processes per build, each with its parse, its Snowflake sessions and its run of the project hooks, and its own selection instead of `selectors.yml`. → One `BashOperator` running `dbt build` from the project venv: the same command as by hand, hooks once, one warehouse wake-up. Per-node results already live in `dq_check_results`. Cosmos would pay off for retrying one model from the UI or for dbt lineage inside Airflow.
80. **The host clock drifted while the Windows Time service was stopped.** The host was 0.91 s behind Binance on 2026-11-21 and 1.77 s behind the next morning: about 0.9 s a day with `w32time` stopped (`Leap Indicator: 3 (not synchronized)`, `Stratum: 0`). The container clock followed the host to the millisecond. After `Set-Service W32Time -StartupType Automatic`, `Start-Service` and `w32tm /resync /force` (source `time.windows.com`, stratum 5) the host was 0.37 s behind and the container followed without a restart; 0.32 s an hour later. Behind is the safe direction (a candle counts as closed a moment later, the 1-candle overlap and the :07 schedule leave minutes of margin). → The time service runs automatically; the clock is part of the as-of contract and is measured against the source, not trusted.
84. **Where Airflow 3.4 runs a callback.** Read in the image: a task's `on_success/failure/retry/skipped_callback` runs in the task's own process, in `task_runner.finalize()`; with LocalExecutor that is the scheduler container, with its environment and files. The DAG's callbacks (`DagCallbackRequest`, reasons `task_failure`, `timed_out`, `all_tasks_deadlocked`) and the failure callback of a task that ended from outside (heartbeat timeout, stuck in the queue, killed process: `TaskCallbackRequest`) run in the DAG processor. The docstring of `BaseNotifier` says the callbacks "run on the Dag Processor", which is half of it. A callback that raises is logged ("Failed to run task callback") and changes nothing. DAG callbacks log neither to a task log nor to the container output, but to `/opt/airflow/logs/dag_processor/<date>/dags-folder/<file>.log` ("Executing on_success dag callback"). → The alert secrets go to the scheduler and the DAG processor; a callback must make sense without the scheduler's files; silence is watched from outside (note 88).
85. **A run timeout produces two failure callbacks; a task failure one.** A rehearsal with `dagrun_timeout` of 40 s and a task sleeping 300 s (2026-11-22): the scheduler marked the run failed and the unfinished task skipped and sent the task SIGTERM; the task ended with exit code -15 and ran its own `on_failure_callback`, and a second later the DAG processor ran the DAG's callback with reason `timed_out`. A plain task failure gives one message: the DAG callback for `task_failure` stays silent by design, `on_failure_callback` runs only on the final try (`load_raw` alerted on try 2/2, its retry was silent), and `upstream_failed` tasks run no callback. → Two messages on a timeout are expected, not a bug.
86. **The Telegram provider is not in the image, and its client logs the token.** The Airflow 3.4.0 image has the Slack, SMTP and HTTP providers but not `apache-airflow-providers-telegram` (in the 3.4.0 constraints: 4.10.1 with `python-telegram-bot` 22.8). That library sends through httpx, which logs every request URL at INFO, and a Bot API URL contains the token (`/bot<token>/sendMessage`); `HttpHook` logs its URL only at DEBUG. → A few lines of `urllib` send the alert: no package in Airflow's environment, the token only in the request, errors without the URL; plain text, since the underscores of dbt test names break Markdown.
87. **`.airflowignore` makes Airflow 3.4 print a deprecation warning of its own.** With a `.airflowignore` in the DAGs folder (glob syntax, the default), parsing logs `DeprecationWarning: GitWildMatchPattern ('gitwildmatch') is deprecated` from Airflow's `file_discovery.py` and from `pathspec`: Airflow calls an API that its own `pathspec` deprecated. The ignore works (`dags/alerting` is imported from `sys.path`, not parsed as DAG files). → Harmless and not ours to fix; recheck with the next Airflow release.
88. **Only an outside watchdog notices silence.** Nothing inside the stack reports that the stack is not running: a machine switched off, Docker Desktop not started, a stuck scheduler or a paused DAG send no alert, and a lost alert is only logged (note 84). healthchecks.io (2026-11-22: free plan with 20 checks and 100 log entries per check, cron schedules with a time zone and a grace time, a Telegram integration, BSD-licensed and self-hostable) waits for a ping; the DAG pings from its success callback, all-skipped runs included. The check runs on `7 */3 * * *` UTC with 1 h of grace: a missing ping alerts about an hour after its slot, so a failed run alerts twice (the task's message at once, the watchdog an hour later). → The ping URL is a secret of sorts (anyone with it can report "alive"); a Snowflake alert on the freshness of the DQ log would have woken the warehouse for every check.
94. **A green run of the DAG can run yesterday's dbt project.** Only `./dags` is mounted; `ingestion/` and `dbt/` are baked into the image. After the image was rebuilt for the loader (2026-11-22) and the dbt models were added later, a manual run succeeded with the new extract task (mounted DAG, baked extract) but `dbt source freshness` checked 3 sources instead of 6 and `dbt build` reported `PASS=117 WARN=2 TOTAL=119`, the graph without the new model; the next run after a rebuild reported the new totals. → Rebuild the image after any change outside `dags/` before a run that should prove it, and read in the task log what was run (node and source counts), not only the task state.
95. **A manual Drain can leave the overdue scheduled slot to run after Unpause.** The DAG was paused from about 19:00 UTC (2026-11-22) with its next slot at 21:07. A Drain run at 21:26 (done 21:28:53) was followed by an Unpause, and `scheduled__2026-11-22T21:07` started at 21:30:39 (8 s, every task skipped: nothing new). Drain unpauses the DAG for its run, so the scheduler created the overdue slot, which waited behind the manual run (`max_active_runs=1`) and ran once the DAG was active. A pause with no slot passing (09:16-09:17 UTC on 2026-11-24) left no extra run. → Harmless here (an all-skipped run costs nothing); before unpausing a DAG whose extra run would cost, check its queued runs.
98. **A umask set in a wrapper leaks to the command, and Docker Desktop keeps Linux modes on a Windows bind mount.** `with-private-keys.sh` set `umask 077` for the key copies and `exec`'d the command with it. An export run through the `project` service (2026-11-24 09:14 UTC) wrote its directory as `0700` and its files as `0600`, owner uid 50000; on the Windows host they look like any other file, but inside another container (the dashboard, uid 1000) they were unreadable ("Permission denied"). The scheduler was spared only because Airflow's `/entrypoint`, which runs after the wrapper, sets `umask 0002` (its exports are `0775`). Docker Desktop stores the Linux owner and mode of files written into a Windows bind mount, and a copy made on Windows carries them along. → The wrapper restores the caller's umask before `exec` (key copies stay `0400`); check what another container sees (`ls -l` inside it), not the Windows Explorer.
103. **A tmpfs without an explicit mode can come back as `755 root` after a restart.** After a Windows restart (2026-11-25 ~12:43 UTC) the original's `airflow-scheduler` looped in `Restarting (1)`: `with-private-keys` failed with `mkdir: cannot create directory '/run/project-keys/50000': Permission denied`. Docker Engine 29.9.3 mounts a tmpfs without a `mode` as `1777` when it creates a container, but when it restarts an existing one the tmpfs takes the mode of the mount point - `/run/project-keys` is not in the image, so Docker had created it `755 root`. The dashboard's `/tmp` tmpfs stayed `1777`: that directory is `1777` in the image. With `--tmpfs /path:mode=1777` the mode survived `docker restart` in a probe. Recovered with `up -d --force-recreate --no-deps airflow-scheduler`; fixed in the original's compose (`/run/project-keys:mode=1777`, commit `e5f002b`). → A tmpfs on a directory the image does not have gets its mode explicitly; check the stack after a restart of the machine, not only after `up`.
104. **After a Windows restart the clock ran ahead of Binance.** On 2026-11-25 ~12:58 UTC, after the restart above, the host was +1.09 s ahead of Binance's server time (three probes, round trip 0.52-0.55 s) and a container +1.20 s; before the restart it was 0.2-1.8 s behind (notes 26, 80). `w32tm /query /status` said `Source: Local CMOS Clock`, `Leap Indicator: 3 (not synchronized)`, no successful sync: the time service was running but had not synchronized since boot. A clock ahead is the direction note 26 warned about (an unclosed candle looks closed); the runs at :07 and the 5-minute publication lag keep it harmless for the schedule. → After a restart, check the clock against Binance before trusting manual runs near the hour; `w32tm /resync /force` (administrator) synchronizes it.

100. **DuckDB 2.0 keeps a connection busy until a result is read to the end, and a locked configuration keeps the time zone.** With duckdb 2.0.1, a `fetchone()` left the result unfinished and the next statement on the same connection failed with `ResourceInUseException` ("connection has an unfinished result"); `fetchall()` (or a cursor per query) works.
